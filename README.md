# agent-eval

AI エージェント環境の質を、あなたのマシンにある Claude Code のログから採点する CLI。

解析は**マシンの中で完結**します。ネットワークは一切使いません。外に出るのは、あなたが自分で JSON を誰かに渡したときだけです（→ [docs/PRIVACY.md](docs/PRIVACY.md)）。

---

## 先に、まだできていないこと

使う前に知っておく必要があるので、最初に書きます。

- **対応しているのは Claude Code だけ**です（→ [docs/OTHER_AGENTS.md](docs/OTHER_AGENTS.md)）
- **点が付くのは 11 軸中 5 軸**です。ほかに 2 軸は「採点しないが必ず出す」もので、残り 4 軸は定義が未確定。理由は軸ごとに出ます
- **窓どうしの比較には 2 回の測定が要ります。** 初回は基準を登録するだけです
- **`recurrencePrevention` が本当に再発を測るのは、互いに素な 2 つの窓が揃ってから**です。窓は「直近 10 稼働日」なので、日々使って**およそ 2 週間後**が最初の 1 回になります
- スコアの絶対値は**他人と比べられません。** 母集団が無いので、意味があるのは自分の時系列だけです

つまり、**入れた日に役に立つ道具ではありません。** 積み上がってから効きます。生ログは Claude Code の保持ポリシーで刈られるので、過去に遡って作ることは原理的にできません（実測: 稼働 121 日に対しログが残っていたのは **5.8%**）。だから**早く入れることだけ**が、後で使えるかどうかを決めます。

## 何を解こうとしているか

既存の Claude Code リーダーボード（CCgather / Viberank / TokenArena / moai-rank）は、どれもトークン量と支出額を競わせています。ですが 2 環境で実測したところ、**総トークンの 94.7〜97.0% はキャッシュ読み出し**で、純粋な生成量は 0.4% 前後でした。量を競う設計は桁で間違っています。

一方、静的な設定採点ツール（skill-doctor / 50-point scorecard / CLAUDE.md grader）はどれもワンショット採点で、時系列も母集団比較も持ちません。

**「質で採点 × 時系列 × エージェント側と人間側の両面」を同時に満たすものが無い。** そこを狙っています。

## 何を測るか

| 軸 | 測るもの | 状態 |
|---|---|---|
| `wastedMotion` | 1 リクエストあたりの無駄な手数 | ✅ 採点 |
| `selfVerification` | 書いたものを自分で確かめたか、失敗から自力で戻れたか | ✅ 採点 |
| `artifactUptake` | 作ったファイルが後で使われたか | ✅ 採点 |
| `recurrencePrevention` | 同じ失敗が戻ってくるか | ✅ 採点（**初回は窓内だけ**。下記） |
| `environmentMetabolism` | 払っている文脈税に見合う資産が残っているか | ✅ 採点 |
| `coverageGate` / `safetyCheck` | 何を読んだか / 権限とフックの状態 | 📋 **採点しないが必ず出す** |
| `firstPassLanding` ほか 4 軸 | 一発着地率、ほか | ⏸ 定義が未確定 |

出力は人間が読めるサマリと、検証可能な JSON の両方です。

**`recurrencePrevention` の初回について。** この軸は 2 層あります。窓の**中で**同じ失敗署名が何度出たか（層 A）と、**前の窓で見た失敗が今の窓に戻ってきたか**（層 B）です。層 B には互いに素な 2 つの窓が要るので、初回は層 A だけで点が出て、`detail.baselineOnly` が `1` になり、落とした項が `axis6-window-not-rolled` として名前で出ます。**点は出ますが、まだ「再発」を測ってはいません。**

## 設計上の確定事項

そのまま実装制約になっています。

- **時系列が先、母集団比較は後** — 時系列はゲーム化に強く、N=1 で成立します
- **提出単位はマシン全体。** プロジェクト別内訳を全件入れ、閾値は設けません
- **率を送らず、分子と分母を生カウントで送る** — 率は定義を埋め込んでしまいます
- **改善アドバイスは原因を断定しない** — 「この症状を出す機序は N 通り。区別するにはこれを見ろ」の形
- **三値（`available` / `not_applicable` / `parse_failed`）は行ごとに判定** — 1 環境に 12 バージョン混在の実測があります

## 実装前に潰してある落とし穴

2 環境の実測で確定済みです。踏む前に書いておきます。

| # | 制約 | 根拠 |
|---|---|---|
| 1 | **走査は必ず再帰** | `glob('*.jsonl')` は `subagents/` を拾わない。全行の 26.7% / 31.2% がサブツリーにある |
| 2 | `isSidechain` をサブエージェント判定に使わない | メイン jsonl では常に false。**パスで判定する** |
| 3 | `toolUseResult.interrupted` を使わない | 2 環境で計 9,995 件のキー出現に対し true が **0 件** |
| 4 | `preventedContinuation` を使わない | 同じく全件 false。**ただし `hookErrors` 非空なら取れる** |
| 5 | `history.jsonl` を定常データ源にしない | 2 環境とも 2026-04-17 で書き込みが止まっている |
| 6 | `pr-link` を汎用軸に使わない | ドメイン依存（284 件 / 0 件） |
| 7 | セッション継続時間を `max - min` で出さない | resume で日を跨ぐため 39 日のセッションが出る |
| 8 | 率を計算する前に分母の定義を書く | 書けないならその指標はまだ実装しない |
| 9 | **ブール値が 0 / 全 false を返したら、同じ事象が別フィールドを探す** | フィールド名は意味を約束しない。実例 3 件 |

制約 9 の実例が制約 4 でもあります。`preventedContinuation` は 278 件すべて false ですが、`hookErrors` 非空は 9 件あり、中身は差し戻し文そのものでした。**ブール値が死んでいて、実データは隣にある。**

## 定義依存の事故（バリデーションの設計根拠）

設計期間 2 日で 4 件起きました。いずれも「データは正しく取れているのに、比較だけが壊れる」形です。

| # | 何の定義 | 振れ幅 | 見つけた側 |
|---|---|---|---|
| 1 | 走査範囲（`subagents/` を含むか） | 1.46 倍 | 環境 A |
| 2 | is_error の分母 | 1.96 倍 | 環境 A |
| 3 | human 発話の定義 | 2.63 倍 | 環境 B |
| 4 | 記録率の分母 | **6.9 倍** | 環境 B |

**うち 2 件は「定義を明示せよ」というルールを書いた本人が直後に破ったもの。** 送る側の規律では止まらないことが 4 回証明されました。

だから**受け取り側で拒否します。** マニフェストの無いペイロードは受け付けません。この実装の中心はそこで、ペイロードの形を決めることではありません。

同じ理由で、**基準が変わった窓どうしの比較は拒否します**（`count-basis-changed`）。数字が出ないことより、意味の違う数字が並ぶことのほうが害だからです。
