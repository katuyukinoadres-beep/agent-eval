## 2026-08-19 — Phase 0 着手前に確定した 6 件

### 決定 1: 時系列を第1弾にし、母集団比較を第2弾に回す

**当初案**: 母集団順位が第1弾、時系列は後。

**採用理由**:
- **時系列はゲーム化に強い**。単調増加／単調減少の軸は例外なく破られる（トークン量は巨大ファイルを繰り返し読むだけ、手戻り率は Edit をやめて Write に寄せるだけ、エラー率は `command || true` の数文字で破れる）。耐えるのは比率と時間微分の 2 つだけ
- **N=1 で成立する**。母集団を待たずに製品が動く
- **層別なしの percentile は情報を持たない**。エージェント環境は用途の分散が桁違いに大きい
- 「エージェントが賢くなり続ける」という製品目的に、時系列のほうが直結している

**却下した論拠**: 「順位がないと誰も他人に見せない」。同一ニッチの自然実験が真逆を示した — ccusage（順位ゼロの個人用集計 CLI）が GitHub 18,000 star に対し、その出力を提出する順位板 viberank は 114 star。Spotify Wrapped は順位ゼロで 2023 年版 20 億インプレッション。WakaTime は順位を 16 ヶ月後に足している。

### 決定 2: 提出単位はマシン全体。プロジェクト別内訳を全件入れ、閾値は設けない

**当初案**: 「きれいなプロジェクトだけ提出する」を防ぐため、加重平均の閾値 M を設ける。

**却下理由**:
- **n=2 の両方が単一プロジェクト支配**（Leon 100% / NiKo 99.6%）。この 2 件から決めた M は、分布が違う環境で破綻する式を「実測で決めた」と称することになる
- n=2 で仮置きした閾値は、後で変えても既提出分を再分類できない
- 部分提出を受け付けないだけで防げる。閾値判定のロジックが不要になる分、実装はむしろ単純

**副次的な根拠**: Leon 環境の `usage_log.csv` には 5 アプリの行が残っているのに、生ログを持つプロジェクトは 1 つだけだった。**今見えているプロジェクト分布は実態ではなく、直近の作業履歴の影**。提出単位をマシン全体に置く理由になる。

### 決定 3: 率を送らず、分子と分母を生カウントで送る

**理由**: 率を送った時点で定義が埋め込まれ、受け取り側で揃え直せない。実測で is_error 率は走査範囲だけで 1.26〜1.46 倍、分母定義で 1.96 倍動いた。生カウントなら定義が変わっても再計算できる。

各指標は `numerator` / `denominator` / `denominatorMeaning` の 3 つ組で持つ。`denominatorMeaning` が無いペイロードは拒否する。

### 決定 4: 走査マニフェストを必須項目にする

**背景**: Leon が「`isSidechain` は全行 false」と報告したが、非再帰 glob が `subagents/` を開いていなかっただけだった。同じバグが is_error 率を 1.46 倍動かしていた。3 日間、両者とも気づかなかった。

**問題の質**: データは両環境とも正しく取れている。**壊れるのは比較だけ**。Leon 6.75%（subagents 除く）と NiKo 2.85%（範囲不明）を同じ母集団に入れると、誰も気づかないまま無意味な順位が出る。

**必須項目**: 走査パス / 再帰の有無 / ファイル数 / 行数 / Claude Code バージョン分布 / `originFieldCoverage` / `activeDaysMethod` / `measuredAt` / `sourceField`。

- `measuredAt` — 同じ環境でも数時間で値が動く（実測でファイル数 156 → 167）。時刻が無いと同一環境の冗長提出を区別できない
- `sourceField` — 同じ指標を別フィールドから取るケースが実際に出た（決定 6）。由来を持たないと、将来 `preventedContinuation` が生き返ったときに旧提出分と混ざる

### 決定 5: `activeDays` は観測された日の和集合で数える

**却下した定義**: `max(git のコミット日数, jsonl の日付ユニーク数)`。

**却下理由**: **Leon 環境で 107.1% を返した**。CSV に `2026-04-17/18/19` の 3 日があるが、初コミットは 04-20 なので git に存在せず、当時の jsonl は刈られている。分母が分子を下回りうる定義だった。

**採用**:
```
activeDays = |union(git のコミット日, jsonl の日付, 外部ログの日付)|
```
分子（外部ログの日付）が分母の部分集合になるので、構造的に 100% を超えない。意味も明確になる — 「作業した証拠のある日のうち、外部ログに入っている割合」。

**限界を明記する**: これは真の稼働日の**下限**でしかない。コミットもログも残さずに終わった日は原理的に見えない。だから `activeDaysMethod: "union-of-observed"` をマニフェストに入れ、将来定義を変えても層別できるようにする。

**併せて暦日数分母の値も持つ**（`recordRateCalendar`）。これは記録率ではなく作業頻度を答える別の指標だが、捨てると「なぜ実日数が少ないのか」が読めなくなる。**2 つの分母を両方持ち、それぞれが何を答えているかをラベルで区別する。**

### 決定 6: 軸6（書いたルール vs 守られたルール）は jsonl 層を必須、外部ログ層を任意にする

**当初案**: データ源は外部 hook ログ。無ければ `not_applicable`。

**却下理由**: 外部 hook ログを持つのは自分で仕込んだ環境だけ。NiKo は `logs/hook_events.jsonl` に 563,613 行あるが、**Leon は 1 行も持たない**（`logs/` は空ディレクトリ、hook 7 本とも書き出しゼロ）。これでは 2 環境中 1 環境が `not_applicable` になり、中心軸が半分の環境で測れない。

**発見**: jsonl から取れた。`preventedContinuation` は 278 件すべて false だが、**`hookErrors` 非空が 9 件（3.2%）**あり、中身は差し戻し文そのもの。9 件全部が `check_response_quality.py` の「質問は一つずつ」ルール違反だった。

**採用**:
- 分子 = `hookErrors` 非空件数、分母 = `stop_hook_summary` 総数。**両方 jsonl にあるので全環境で比率が出せる**
- 外部ログを持つ環境は、さらに細かい分解（warned / triggered の区別）ができるので**上乗せの任意層**に回す

## 横断する教訓 — なぜバリデーションを受け取り側に置くのか

設計期間 2 日で定義依存の事故が 4 件起きた。**うち 2 件は「定義を明示せよ」というルールを書いた本人が直後に破ったもの。**

- NiKo はルール制定の数時間後に、Leon の数字を検証せず設計書に取り込んだ
- Leon は「パーサが静かに 0 を返す」と自分で警告した直後に、非再帰 glob をやった

**送る側の規律では止まらないことが 4 回証明された。** だから受け取り側で拒否する。マニフェストの無いペイロードは受け付けない。

そしてこの事実自体が製品の芯になっている:

> **単一環境で自己採点するツールは、自分のパーサのバグを永遠に検出できない。**

三値フラグも走査マニフェストも、結局は「外部から検算できる形で出せ」という同じ要請の別名だった。この 2 日で、Leon は非再帰 glob を、NiKo は推定値の混入を見つけた。どちらも自分では見つけられなかった。

## テストの方針

**拒否条件は、拒否できることを先に示してから通す。**

Leon 環境で `usage_collector.py` の rebuild バグを直したとき、`starting_rows` を `return {}` に戻してテストが落ちること（exit 1）を確認してから修正版を通した。同じ形を V-1〜V-8 の各条件に適用する。

**フィクスチャは実際に起きた事故そのものを使う**:

| 実際の事故 | 拒否/警告すべき形 |
|---|---|
| 非再帰 glob | `scope: "all"` なのに `subLineRatio: 0` |
| is_error の分母未明示 | 率だけあって `numerator` / `denominator` 無し |
| human 定義の乖離 | `originFieldCoverage: 0.034` |
| 記録率 107% | `recordRate.numerator > denominator` |
| ブール値が死んでいる | `sourceField` 無し |

実際の事故を固定しておけば、同じ穴をリグレッションとして二度踏まない。今回の 4 件は全て「検出器が動くことを確かめなかった」形だった。

## 2026-08-20 — 仕様書2本の食い違い3件（S7a で確定）

S7 の実装に入る前に窓の定義を読み直したところ、`agent_eval_axes_v2.md` と `submission_payload_spec_v1.md` が3箇所で食い違っていた。3件とも**受信側が黙って比較に失敗する**形で、例外にはならない。

### 1. `windowSource` の第2値: `observed` か `measured` か

| 出典 | 値 |
|---|---|
| `submission_payload_spec_v1.md` §2 | `"setting" \| "observed"` |
| `agent_eval_axes_v2.md`（2箇所） | `"setting" \| "measured"` |

同じものを指す2つの語。閉じた union の照合は文字列一致で行うので、送信側が `observed`・受信側が `measured` なら**どの環境も一致せず、片方が黙って落ちる**。

**採用: `observed`。** ペイロードの語彙はペイロード仕様が決める。ただし受信側が軸仕様から実装されていれば1行の差なので、AB-87 で確認に出した。

### 2. `activeDays` が同一環境で2つの値を持つ

| パス | 値 | 意味 |
|---|---|---|
| `window.activeDays` | **17** | 人間発話が1件以上ある日。全軸の分母スコープ |
| `externalLog.activeDays` | **18** | 何らかの証拠がある日の和集合。記録率の分母 |

どちらも正しく、答えている問いが違う。危険なのは**親オブジェクトを見ずに `activeDays` を読むと 5.9% ずれる**こと。事故#1〜#4 と同じ形。

**対策:** 型を分けた（`WindowDaysMethod` = `'human-turn-days'` / `ActiveDaysMethod` = union 系）。ラベルを取り違えた値は構築できない。加えて 2 つの検算ルールを追加:

- **V-13** — `externalLog.recordRate.denominator` は `externalLog.activeDays` と一致すること。分数の中にしか存在しない分母は、何とも突き合わせられない
- **V-14** — `window.activeDays ≤ externalLog.activeDays`。人間発話があった日はその発話を読んだ jsonl を残しているので、和集合に必ず含まれる。**大小逆転は構造的に不可能**＝入れ替えの検出器になる

### 3. base 自身が矛盾していた（main 上の実バグ）

`windowSource: 'setting'` と `cleanupPeriodDays: null` が同居していた。「設定から読んだ」と言いながら「何を読んだかは無い」状態。このマシンには4スコープのどこにもキーが無いので、正しくは `observed`。

**V-15** を追加した。`setting` なら period 必須、`observed` なら period は null。

### 陽性対照

| 対照 | 結果 |
|---|---|
| V-13/14/15 を `add()` で握りつぶす | 該当の拒否テスト4件だけが失敗、他 111 件は無傷 |

1 回目の対照は perl の置換が一致せず**対照が走らないまま 115 件通過**した。`grep -c` で「対照が入っていること」を先に確認する手順に変えた。検出器を無効化したつもりで無効化できていない場合、出力は「全部通る」で、成功と見分けがつかない。

## 2026-08-20 — S7b: 窓と外部ログの生成側

### 実機で出た数字（Python 独立実装と照合済み）

```
人間発話日 (origin.kind=='human')  =  5   2026-08-16 〜 08-20
user 行のある日                    =  9   ↑ + 2026-07-08〜07-11
jsonl の日                         =  9
git コミット日                     = 15   2026-04-20 〜 08-20（2リポ）
外部ログ (usage_log.csv)           = 42 行 / 19 日
証拠日 = union(git, jsonl, 外部)   = 23
記録率                             = 19/23 = 82.6%
cleanupPeriodDays                  = null（4スコープ全てに不在）
```

人間発話日・user行日・jsonl日・git日・cleanupPeriodDays の5項目は **TS 実装と Python 実装で完全一致**。

### 発見1: 最初のゲートが origin カバレッジで決まっている

仕様は `activeDays < 5` で環境まるごと `not_applicable`（総合点を出さない）。このマシンの実測は **ちょうど 5**。

そして `activeDays` = 人間発話日は `origin` フィールドを持つ行からしか数えられず、**このマシンの origin カバレッジは 3.11%**。7月の4日間は user 行があるのに origin が1件も無いため、稼働日として数えられていない。

つまり **1日ずれれば環境が採点対象から外れ、どちら側に落ちるかは「どのバージョンがログを書いたか」で決まる**。作業量ではない。

**対策:** `window.userRowDays`（user 行のある日 = 9）を併記する。閾値を発明せずに、受信側が感度を自分で計算できる。加えて **V-16**（人間発話日 ⊆ user行日 ⊆ 証拠日）で3値の入れ子を固定。

### 発見2: `externalOnlyDays` が構造的に常に 0 だった

「外部ログにしか無い日」を**分母集合と比較**して数えていた。ところが分母は外部ログを和集合に含んでいるので、**実機では必ず 0**。

これは `isSidechain` / `toolUseResult.interrupted` / `preventedContinuation` と同じ形 — 定数ゼロを返し続けるフィールドは、動いている検出器と見分けがつかない。

**修正:** 生ソース（jsonl ∪ git）と比較する。実機で **7 日**。107% を生んだのはまさにこの種の日。

### 発見3: 記録率が 1 を超えられない理由は2つあり、どちらか片方では検証にならない

- 外部ログの日を分母（和集合）に入れている
- 分子を分母集合との**交差**で作っている

`numerator <= denominator` だけを assert すると、**どちらを外しても通る**。実際、最初に書いたテストは両方を外さないと落ちなかった＝何も検証していなかった。

各機構が固有に生む値で固定し直した:

| 対照 | 落ちるテスト | 症状 |
|---|---|---|
| 和集合から外部ログを外す（= max 相当） | 「log-only day を分母に入れる」 | `evidenceDays` 6 → 3 |
| 交差をやめて外部ログ日数をそのまま分子に | 「分母が持つ日だけ数える」 | `makeMetric` が「分子4 > 分母3」で拒否 |

### git に聞くのはコミット日だけ

`GIT_ARGS = ['log', '--format=%cd', '--date=short']` を定数にし、argv 自体をテストで固定した。git クライアントが入る最初の場所は、PR 数・マージ帰属・revert 率を足すのが最も安い誘惑になる。v1 §15 はそれらを reject 済み（`pr-link` は Leon 284 / NiKo 0 で、ホストの差を測ってしまう）。

### プロジェクト名からリポジトリパスは復元しない

`C--Users-katuy-Yama-Agent` は `C:\Users\katuy\Yama-Agent` にも `C:\Users\katuy\Yama\Agent` にも復号でき、名前の中に区別材料が無い。デコーダは大半で当たり、外れたときは**「コミットの無いリポジトリ」に見える** — 静かなゼロ。git 日はリポジトリを明示的に渡されたときだけ数え、`activeDaysMethod` がそれを言う。

### 行数のドリフト

Python 29,652 → TS 29,892 → TS 29,922 と単調増加した。進行中セッションが自分のトランスクリプトに書き足しているため。**同一環境の2回の提出を区別するにはマニフェストに `measuredAt` が要る**ことの実データ。

## 2026-08-20 — S11a: 環境収集

### 実機で出た数字（Python 独立実装と全項目一致）

```
permissions  allow=67  deny=3  ask=0            （user 16 + project 0 + local 51）
  分類       unrestrictedExec=0  cliWildcard=27  scriptPathFixed=24  exact=16
skills       .claude/skills/*/SKILL.md =  0

hooks        5 件 / 3 イベント（PreToolUse / SessionStart / Stop）
mcpServers   1 件（~/.claude.json の top-level）
```

### 発見: MCP サーバー定義は settings 4スコープに無い

`settings*.json` の4スコープは**全て 0**。実体は `~/.claude.json` の top-level `mcpServers`。

これは AB-87 で NiKo に投げた Q-11（`mcpUsed` の分母ソース）の実測回答。settings スイープだけで作った収集器は **`mcpUsed` の分母を 0 にする** — V-4 は通り、W-6 の下限 100 未満、結果 0/0 の穴。

読む先を `.mcp.json` / `~/.claude.json` / `~/.claude/settings.json` の union にした。

### permissions は「マージ」であって「上書き」ではない

Claude Code は全スコープのリストを適用するので、実効面は和集合。最高優先スコープだけを見ると **このマシンで 67 件を 16 件と報告する**。

### 文字列は載せない — 実データで確認した理由

このマシンの allow に含まれるもの:

```
node scripts/emit-service-key.mjs:*
node scripts/ban-test-accounts.mjs:*
node ../anki-new/scripts/emit-service-key.mjs:*
```

スクリプト名が「このマシンが何をして良いか」を説明し、相対パスが**別プロジェクト名**を運ぶ。仕様のスケッチ（`"effectivelyUnrestrictedPatterns": ["Bash(python:*)"]` を文字列で送る）は、同じ問いに `{class, count}` で答えられる。

### 分類器は allow だけに掛ける

`deny` のワイルドカードはリスクの逆。同じに数えると、**丁寧に締めた環境ほど開いて見える**。

### 3つのゼロに全て陽性対照を付けた

このマシンで 0 を返す3項目は、壊れた収集器の出力と同じ:

| 0 になる項目 | 対照 | 結果 |
|---|---|---|
| `unrestrictedExec` | 実データに `Bash(python:*)` を1件足す | 0 → 1 |
| `skills/*/SKILL.md` | 入れ子レイアウトの glob 結果を注入 | 0 → 1 |
| settings 内の MCP | `~/.claude.json` を読む経路 | 0 → 1 |

`unrestrictedExec` の対照は**単体テストではなく実データ経路**で取った。テストの偽データで通る分類器が、実ファイルの形では動かないことがあるため。

### 3クラスは allow の分割ではない

`unrestrictedExec + cliWildcard + scriptPathFixed + exact = allow` だが、`exact`（ワイルドカード無し）はリスククラスではない。3クラスはリスクの部分集合。

## 2026-08-20 — S8 + 組み立て + `scan`: 初めて通しで動いた

出力は **11,334 バイト**。`katuy` / `Yama-Agent` / `anki-new` / `emit-service-key` / ドライブレター、いずれも **0 件**。

### 点は1つも出していない

率→点の変換式は v1 軸文書にあり、このリポジトリに無い。埋めるために式を作れば、**誰も擁護できない数字を画面に出す**ことになる。全軸 `score: null`。

代わりに `unavailableReasons` を持たせ、**2種類の理由を分けた**:

- `too-few-clusters` — 実測（11 クラスタ < 最小 20）。仕様が与えた閾値に対する測定結果

## 2026-08-23 — クラスタの畳み込み（P4 設計レビューの指摘 #3 を検証）

P4 の設計ワークフローが「`counts.sessionIds` は行の `sessionId` から作っており、v2:962 の `sub は親 session_id に畳む` に反する」と指摘した。**クラスタ数は最小分母（20）の判定に直結し、CI の可否を決める。**

### 実測: 指摘はこのデータでは誤りだった

```
行の sessionId (distinct) = 12      ファイル位置由来の親 id = 12
  うち main 行由来        = 12      sub にしか無い id       = 0
  行 id ⊆ 親 id           = True
```

サブエージェント行は**すでに親の sessionId を持っており**、新しい id を持ち込んでいない。現行実装の数え方は、このマシンでは仕様の畳み込みと一致する。

### ただし一致は偶然であって保証ではない

サブエージェントのトランスクリプトが自分の id を持つ環境では、**クラスタ数が黙って増える**。増えた先が 20 を超えれば `belowMinDenominator` が false になり、出るはずのない CI が出る。

数字は変えず、**根拠を偶然から構造に変えた**:

- クラスタはファイルの位置から畳む（`file.sessionId`）
- 行の `sessionId` はそれと突き合わせ、食い違いを `sessionIdMismatchRows` として数える

### 検出器の陽性対照を2段で取った

**測定器側** — 一時ツリーに「sub が独自 id を持つ」形を作ると (行 2, 親 1) と差が出る。同じ形で親 id を持たせると (1, 1)。指摘を「誤り」と判定する前に、**差を検出できることを先に示した**。

**実装側** — `scan.test.ts` のコーパスは行が `s1`・ファイルが uuid という乖離ケースなので、`sessionIdMismatchRows > 0` をテストで固定した。実機の 0 は、**発火できることが示された検出器の 0**。

### 副産物

このコーパスは今まで「行の id を集める」実装に合わせて `['s1']` を期待していた。畳み込みに変えたことで**期待値がファイル名側に移り**、コーパス自体が乖離の実例として機能するようになった。

## 2026-08-23 — P4 基盤（状態ディレクトリ・MAC・鍵）

P4 の設計を9エージェントのワークフローで固めた（読解4 / 設計1 / 敵対レビュー3 / 統合1）。本コミットは §1（配置）・§5.3（MAC）・§5.4（鍵）の実装。

### ディレクトリは無防備な状態で存在できない

「mkdir してからガードを書く」では、その間に落ちると**MAC を含むディレクトリがガード無しで残る**。staging 名で組み立て、`.gitignore` を中に入れてから `rename` する。rename は NTFS でも POSIX でも原子的で、**最終名で見えた時点でガードは既に中にある**。

`.gitignore` は毎回読み直して、`*` の行が無ければ書き直す。守っている相手は「数か月後にエディタやバックアップツールや `git clean` がドットファイルを消す」で、それは何も告げない。

### git 追跡の拒否条件を狭めた

設計初稿は「`.git` が STATE_DIR かその上位にあれば拒否」だった。**ホームディレクトリを git 管理している人は `~/.git` を持つ**ので、この条件では毎回・永久に拒否され、このモジュールが守るはずのものを失わせる。

リポジトリの中にいることはリスクではなく、**コミットされていることがリスク**。`git ls-files --error-unmatch` が 0 で返るときだけ拒否し、`--state-dir` という逃げ道を示す。

### 鍵は毎回変えられない — 変えると満点になる

軸6の窓跨ぎ再発は MAC 集合の交差。鍵が変われば**交差は空**になり、再発率 0 ＝「同じ失敗を二度としない環境」として満点が出る。v1 §16 が挙げた攻撃を、事故で踏む形。

一方で永続鍵は永続的な秘密。**解決はローテーション計画ではない**: ローテーションには平文が要り、平文は設計上捨てているので、新鍵は旧集合を引き継げない。誰も払わないコストなので、鍵は実質 write-once。実際に効く緩和は (a) 鍵をストアの外に置く (b) 集合の保持期間を切る、の2つだけ。

### 交差の可否は epoch ではなく fingerprint で見る

鍵ファイルと `key.epoch` を一緒に消してスナップショットだけ残ると、新しい鍵が **epoch 1 を名乗る**。epoch で判定すると2つの別鍵が同じラベルを共有し、交差が空になって満点が出る。`fingerprint` 不一致で拒否し、**epoch が一致して fingerprint が違う場合を `key-identity-conflict` として別名で報告**する（何も異常に見えないぶん、こちらのほうが悪い）。

### ファイル名の前方一致が罠

`~/.agent-eval-key` は `~/.agent-eval` を**前方一致で含む**。`startsWith` で「ストアの中か」を判定するコードは、鍵をストアの中と誤判定する。バックアップ除外なら鍵を巻き込み、クリーンアップなら**比較の唯一の手段である鍵だけを消してスナップショットを残す**。テストで固定した。

### 設計書の算術が1件誤っていた

「`bytesRead` は 1e9 に達し、1e9 × 1e4 は 2^53 を超える」と書かれていたが、**1e13 < 9.007e15** で超えない。ガード自体は残したが、根拠を実際の閾値（約 9.007e11）と「この尺度を取るフィールドは全て率か 0-100 の点なので、これを超える値は count が誤ったコンストラクタに来た印」に書き換えた。**テストを書いたら落ちて分かった。**

## 2026-08-23 — P4 正準形とハッシュ

```
1回目: seq 1  prev={"kind":"genesis"}
2回目: seq 2  prev={"hash":"sha256:4e091ac0f1ad..."}
chain: length 2, continuous true, consecutiveTail 2, breaks []
```

**陽性対照**: 1つ目を書き換えると `hash-mismatch` が seq 1 と seq 2 の**両方**に出て、`consecutiveTail` が 2 → 0 になる。**過去を書き換えると、書き換えた行だけでなく履歴全体を失う。**

保存済みハッシュも一緒に書き換える（実際に試みられる偽造）ケースは、**子が捕まえる**。そこがチェーンの性質の在り処。

### 検出するもの

連番の欠落 / フォーク / 読めない本体 / sidecar の削除・改変 / 鍵の fingerprint 変化 / 時計の逆行。

**時計は記録するだけで補正しない。** 黙って補正するのが「もっともらしい誤った数字」の作り方。

### 何を establish しないかを名前で持つ

`NOT_ESTABLISHED` は免責文ではない。鍵はローカル・ハッシュ関数は公開なので、**ストアと鍵に書き込める者は自己整合的な偽の履歴を作れる**。

CLI は "verified" ではなく **"self-consistent"** と書く。テストは主張ではなく**実演**する — ゼロから作り直したチェーンは、育ったチェーンと**まったく同じくらい clean に検証される**。

### 走査範囲を verdict に持たせる

**走査していない 0 は、綺麗なチェーンと見分けがつかない。**

### スナップショット行は毎回出す

```
snapshot   wrote #2 (15f9b5a250bd), chain 2 self-consistent — 3 block(s) absent
snapshot   not written (--store to keep history)
snapshot   REFUSED: locked — another run holds the lock
```

**黙って書けなかったスナップショットは、1窓あとに「比較できない」という形で見つかる。** パスは載せない（OS ユーザー名を含み、この出力は issue に貼られる）。

## 2026-08-23 — 窓の Stage A: 日の定義

設計ワークフロー（11エージェント / 4案 / 3レンズ）の結論は **scope-per-axis**（行は落とさず、集計に日を付け、採点時に窓を当てる）。単一パスの保証も、parentUuid 連鎖も、`seen` 集合も、CENSOR_DAYS も、`sessions-close` も、**すべて壊れない**。境界はスキャン後に `humanTurnDates` から求まる — `scan()` が既に返している。

Stage A としてまず**日の定義**だけを入れた。

### `ts.slice(0, 10)` は「パースしない UTC 日」だった

タイムゾーンを名乗らず、パースもしない。`'9999-99-99T00:00:00Z'` から `'9999-99-99'` を返す。

`dayOf(ts, offsetMinutes)` に置換。パースできなければ **null**（推測しない）。

### 日の境界が窓の中身を決める。実測:

| 境界 | human-turn 日数 | 窓10日での効果 |
|---|---|---|
| UTC | 10 | **全選択（フィルタが効かない）** |
| +05:30（この機械の実オフセット） | 10 | **全選択** |
| +09:00 | 11 | 2026-07-08 が落ちる |
| -05:00 | 9 | 全選択 |

### 🚨 この環境では、窓を入れても数字は1つも動かない

稼働日が10、窓が10。**死んだフィルタと正しい窓が、この機械の数字だけでは区別できない。** だから:

- `window.dayBoundary` / `window.activeDaysUtc` / `window.activeDaysInWindow` / `truncated` / `windowStart` / `windowEnd` を全部 payload に出す
- サマリに `10/10 in window ... boundary +05:30, 10 under UTC` と出す。**`activeDaysInWindow === activeDays` は「窓が何も切らなかった」という事実**
- 10稼働日を超える fixture でのテストは省略不可

### `measuredAt` の既定を UTC からローカルオフセットに変えた

**稼働日は「誰かの一日」**で、それはその人の真夜中で終わる。9時間進んだ機械で UTC 打刻すると、毎晩が2日に割れる。窓は日を数えるので、これは定義を変えてしまう。

### docstring が窓の定義を間違えていた

`scan.ts` と `window.ts` の両方が `humanTurnDates` を「`origin.kind === 'human'` の日」と書いていた。実装は `notHumanBecause(row) === null`（P1）。

**`origin.kind` はこの環境の user 行の 2.7% にしか無い。** interface を信じて実装した人は稼働日**5日**に着地する — `MIN_ACTIVE_DAYS = 5` の抑止ゲートの1日手前。

- Stage B: 約45個の集計器を日キー化 + `restrict(counts, scope)`。**負の対照**（`restrict(dated, null)` が今日の `scan()` と完全一致）が必須

## 2026-08-24 — 窓は「完了した稼働日」で作る（設計の未解決点を実測で閉じた）

設計が open question として残していた「最新の未完了日を窓に入れるか」。**入れる実装のまま日付が変わり、症状が実データで出た。**

### 症状

```
稼働日ごとの行数（+05:30）
 *2026-07-08   2285 行   ← 窓外に押し出された
  2026-08-23  11235 行
  2026-08-24     77 行   ← これが増えたせいで転がった
```

**77行の未完了日が、2,285行の完了日を追い出した。** コーパスの 5.7% が、0.2% が到着したせいで窓を出た。

### 1日はいつ完了するのか — 実測

各稼働日の作業が、その時刻までにどれだけ済んでいたか（中央値）:

| 時刻 | 完了率 |
|---|---|
| 09時 | **6.9%** |
| 12時 | 37.8% |
| 15時 | 46.3% |
| 18時 | 76.1% |
| 21時 | 100% |

**進行中の日を「1稼働日」として数えると、測っているのは環境ではなく実行した時刻。** 朝に走らせるか夜に走らせるかで分母が変わる。

### 決定

窓は **`measuredOn` より厳密に前の稼働日**だけで作る。実行日は `inFlightDay` として**報告し、採点しない**。

損失は「今日の作業は明日まで採点されない」こと。得るのは:

- **同じ日に2回走らせたら、まったく同じ証拠を選ぶ**。窓を比較する道具にとって、これが一番要る性質。以前は朝と夜で別の窓になった
- 部分的な日が完了した日の枠を奪わない
- `truncated` は「埋められたはずの日数」に対して判定する。in-flight 日は候補ですらなかったので、それで truncated と言うのは嘘

例外は**完了日が1日も無い初回**だけ。ここで拒否すると新規ユーザーに「明日また来い」と言うことになるので、in-flight 日を使い `includesInFlightDay: true` と明示する。

### 実測の変化

```
before  10/11 in window (2026-07-09..2026-08-24)   ← 2,285行の日が欠けている
after   10/11 in window (2026-07-08..2026-08-23)   ← 完了10日
        today 2026-08-24 in flight, not scored
```

## 2026-08-24 — Stage B1: 日キー化の土台と `restrict()`

設計どおり「行は落とさず、集計に日を付け、選択で窓を当てる」。**リデューサが見るコーパスは変わらない**ので、parentUuid 連鎖・`wastedTracker.seen` の初出・セッション別 `seenClasses`・`lastWrite` と CENSOR_DAYS・`sessions-close` の**どれも壊れない**。

### カウンタを2つに分けた（宣言の強制）

- **`DayCounts`（24項目）** — 日に属する。行カウンタ、トークン、denialKinds、todoWriteUsed
- **`AllTime`（19項目）** — 構造上コーパス全体。既定に流れ込むのではなく**宣言が要る**

`AllTime` に置いた理由を1つずつ `ALL_TIME_REASONS` に書いた。一番鋭いのは `linesParseFailed`: **パースできない行にタイムスタンプは無い**ので、窓に入れた版は構造的にゼロになり、それに乗っているパース失敗ゲートは「整った形のゼロを返す検出器」になる。

### 負の対照

`restrict(counts, null)` は**スキャンが返したオブジェクトそのもの**（`toBe`）。日バケツから組み直すと、テストが「組み直し」を検査してしまい元と比べなくなる。

対になる半分も書いた: 1フィールドだけ潰した stub と比べて `false` になること。**そうしないと `toBe` が通っている理由がデータと無関係でも気づけない。**

### fixture は12日。この機械では窓が空振りするから

この機械は完了稼働日10・窓10 なので**窓が全選択**する。実データだけでテストを書くと、**何もしないフィルタが全部通る**。だから fixture を12日にして、10日窓が2日を確実に落とすようにした。

### 日付なし行はどの窓にも入らない

テストを書いたとき自分の期待値を間違えた（差3のはずが4）。正しいのは4 — 除外日3行 + **日付なし1行**。日を持たない行を「一番新しい窓」に入れるのは、失われた観測の復元ではなく**捏造**。

### まだ窓が当たっていないもの（`NOT_YET_WINDOWED` に実名で列挙）

`taskBundles` / `wasted` / `errorRepeats` / `signatures` / `verification` / `editedPaths` / `perSession` / `perProject` / `metabolism` / `manualEdits`。

**窓の分子を全期間の分母で割ると、誰にも名前の付けられない率になる。** 列挙してあるのは、この変更が失敗する主な形が「窓を当てた軸の中に1個だけ全期間のカウンタが残る」だから。リストは、カウンタが動いたら誰かが編集しないといけない形にしてある。
