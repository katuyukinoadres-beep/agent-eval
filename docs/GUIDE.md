# 取扱説明書 — 出力の読み方

このツールの出力は、**数字より「なぜその数字が無いか」のほうが行数が多い**設計になっています。読みにくく見えますが、意図的です。根拠のない数字を 1 つ画面に出すことが、このプロジェクトが対策しようとしている失敗そのものだからです。

以下、`scan --summary` の出力を上から順に説明します。

---

## 0. 最初に覚える 3 つ

| | |
|---|---|
| **窓** | 直近 **10 稼働日**。カレンダー日ではなく「実際に働いた日」 |
| **今日は数えない** | 書きかけの日は 1 日の断片。窓の 1 枠を使わせません |
| **点は他人と比べられない** | 母集団がありません。**意味があるのは自分の時系列だけ**です |

**そして、いちばん先に読むべきは点数ではありません。** 初回から出て、そのまま行動に
つながるのは §3.5「バージョン別」と §6「使われていない資産」の2つです。点数は
規模が要りますが、この2つは要りません。

---

## 1. `scanned` — 何を読んだか

```
scanned    329 files, 48093 lines, 0 unparsed
           0 unreadable, 0 with no rows
           5354 undated (in no window), 8253 rows out of window
           main 27902 / sub 20191 (share 0.4198)
```

| 項目 | 見方 |
|---|---|
| `unparsed` | 読めなかった**行**。**1%** を超えると `W-5` 警告、**5%** を超えると環境ごと採点対象外 |
| `unreadable` / `with no rows` | 開けなかった / 中身が無かった**ファイル**。**ゼロでも必ず印字します** |
| `undated` | タイムスタンプの無い行。**どの窓にも入りません**（今の窓に入れるのは観測ではなく捏造です） |
| `rows out of window` | 窓の外の日の行 |
| `main / sub` | サブエージェントの行が全体のどれだけを占めるか |

**`sub` の比率は落とし穴の跡です。** サブツリーを走査しない実装だと全行の 3 割前後が消え、それだけで数字が 1.46 倍ずれます。

---

## 2. `origin` — この行はどれくらい信用できるか

```
origin     376/13541 of user rows
```

「人間の発話かどうか」を明示しているログ行の割合です。**ここが低いと、人間の手数を分母にする指標が実際より低く出ます。** 10% を下回ると `validation` に `W-1` フラグが出ます。

これは環境の欠陥ではなく **Claude Code のバージョン差**です。古いバージョンで書かれたログにはこのフィールドがありません。

---

## 3. `window` — いつの話をしているか

```
window     11 human-turn days, 11 user-row days, observed
           10/11 in window (2026-07-08..2026-08-23), boundary +05:30, 11 under UTC
           today 2026-08-24 in flight, not scored
           scored over the window: 4/4 axes
```

- **`10/11 in window`** — 稼働 11 日のうち 10 日を採った、という意味です。**`11/11` なら窓は何も切っていません。** 動かなかった数字は「効いている証拠」にはならないので、ここは必ず見てください
- **`boundary +05:30, 11 under UTC`** — 日の変わり目をどこに置いたか。**UTC で数えると日数が変わる場合、その数も併記します。** 深夜に働く人ほどここで結果が変わります
- **`today ... in flight, not scored`** — 今日はまだ書きかけなので数えていません
- **`scored over the window: 4/4 axes`** — 点の付いた軸のうち、何本が窓の上で計算されたか。**この行は宣言ではなく実測です**（各軸が自分の基準を持っていて、そこから導出しています）

---

## 3.5 `by version` — 「最近ばかになった気がする」を数字にする

```
by version
           2.1.173         —      44 rows 2026-07-08..2026-07-08  (4 calls — under the floor, no rate)
           2.1.204    0.0209    4899 rows 2026-07-08..2026-08-16
           2.1.233    0.0177   18626 rows 2026-08-16..2026-08-20
           2.1.235    0.0201   36305 rows 2026-08-18..2026-08-30
           2.1.251    0.0152    7328 rows 2026-08-30..2026-09-03
```

左から **バージョン / ツール呼び出し1回あたりの失敗率 / 行数 / その版を使っていた期間**。

**なぜバージョンで切るのか。** ログの中で「**あなたのせいではないと確実に言える変化**」は
これだけだからです。日付で切ると、あなたの仕事が難しくなっただけの変化と区別がつきません。

上の例の読み方: 規模の大きい3版が 0.0177 / 0.0201 / 0.0152 で**ほぼ横ばい**。
つまりこの環境では「バージョンが上がって悪くなった」という事実は**ありません**。

### `—` と出ている行

**呼び出し数が下限（200件）に届いていないので、率を出していません。** `44 rows` の行は
呼び出し4件です。仮に率を出すと `0.5000` になり、他の行の `0.02` と並んで「25倍悪化」に
見えますが、**4件のうち2件失敗しただけ**です。分子と分母は JSON 側に残してあるので、
自分で束ねたい人は束ねられます。

### 落とし穴（これは必ず読んでください）

**バージョンが変わった時期に、あなたの仕事も変わっています。** 難しい案件をやっていた
2週間をまたいで版が上がっていれば、その版は悪く見えます。**これは版のせいではありません。**

だから率だけでなく**期間と件数を同じ行に出しています**。判断するときは:

- 期間が短い版は疑う（`2026-08-16..2026-08-20` は5日間です）
- 件数が近い版どうしで比べる
- 版の切り替わり日をまたいで**前後1週間ずつ**を見る

---

## 4. `evidence` / `record` — 記録の習慣

```
evidence   11 days (union-of-observed(jsonl))
record     0/11
```

働いた日のうち、何日ぶんの記録が残っているか。`--external-log` を渡していない場合、分子は 0 のままです。**0/11 は「記録していない」であって、「測れていない」ではありません。**

---

## 5. `store` / `snapshot` / `vs prev` — 履歴と比較

```
store      not opened (--store to open it)
snapshot   not written (--store to keep history)
vs prev    no store opened
signatures unsigned — the set is empty, not the environment
```

`--store` を付けると、ここが履歴になります。

- **`snapshot` は成否にかかわらず必ず出ます。** 黙って書けていないと、それに気づくのは「比較したい 1 窓あと」になるからです
- **`signatures unsigned — the set is empty`** — 「署名できなかった」ではなく「**署名すべきものが無かった**」です。この 2 つは違うので言い分けています

### `vs prev` の読み方

```
vs prev    window-10d, 4 axes: wastedMotion +1.2, selfVerification -0.4, ...
           (none can be called a change: no interval yet)
           composite: 55.7 → 56.9 (+1.2)
```

**`+1.2` は「改善した」という意味ではありません。** このツールは、区間が 0 をまたがず、かつ大きさが下限を超えたときにしか「変化した」と呼びません。今はまだ区間が無いので、**差は全部表示され、どれも変化とは呼ばれません。**

`no delta — <理由>` と出ることがあります。**バグではなく、比較の拒否です。**

| 理由 | 意味 |
|---|---|
| `count-basis-changed` | 数え方が変わった。**意味の違う数字を並べるより、出さないほうがましです** |
| `composite: withheld` | 2 つの窓が同じ軸を測っていなかった |

---

## 6. `gate` / `axes` — 点と、点が無い理由

```
gate       passed
axes       6/11 available
           artifactUptake          60.57
           recurrencePrevention    55.79
           selfVerification        32.07
           wastedMotion            62.39
```

`gate` が `passed` 以外なら、**環境ごと採点対象外**です（理由がそのまま並びます）。

**`6/11 available` なのに 4 行しか並んでいないのは正常です。** available な 6 つのうち
2 つ（`coverageGate` と `safetyCheck`）は**設計上、点を付けない軸**だからです。何を読んだか、
どんな権限設定かを報告するのが仕事で、順位を付けません。JSON 側では `detail` に中身が
入っていて、`notScoredByDesign: 1` が「点が無いのは測れなかったからではない」ことを示します。

### 各軸の意味

| 軸 | 高いと何が言えるか |
|---|---|
| `wastedMotion` | 1 リクエストあたりの無駄な手数が少ない |
| `selfVerification` | 書いたものを自分で確かめ、失敗から自力で戻れている |
| `artifactUptake` | 作ったファイルがその後も使われている（作りっぱなしでない） |
| `recurrencePrevention` | 同じ失敗を繰り返していない |

### `recurrencePrevention` の初回は「再発」を測っていません

この軸は 2 層あります。**窓の中**で同じ失敗署名が何度出たか（層 A）と、**前の窓で見た失敗が戻ってきたか**（層 B）です。層 B には互いに素な 2 つの窓が要ります。

初回は層 A だけで点が出て、こうなります:

- `detail.baselineOnly` が `1`
- 落とした項が `axis6-window-not-rolled` として**名前で**出る

**点は出ますが、まだ再発を測ってはいません。** 窓 1 本ぶん（およそ 2 週間）使い続けると本来の値になります。

---

## 7. 点が無い軸の理由

```
           5 × definition-pending
           4 × too-few-clusters
```

**この行がこのツールの本体**です。「小さい環境だから測れない」と「まだ実装していない」は、まったく違う話なので言い分けています。

| 理由 | 意味 | どうするか |
|---|---|---|
| `definition-pending` | 定義が未確定。**実装されていません** | 待つ（あなたの側にできることはありません） |
| `too-few-clusters` | セッション数が下限に届いていない | 使い続ける |
| `insufficient-edit-intervals` | 編集の間隔サンプルが足りない | 使い続ける |
| `no-artifacts` | 成果物が観測されていない | 使い続ける |
| `no-failures` | 失敗が無いので再発を測れない | **良い状態**です |
| `environment-gated` | 環境ごと対象外（`gate` を見てください） | `gate` の理由に従う |

## 6.5 使われていない資産 — いちばん行動しやすい数字

JSON 側（`agent-eval scan` の出力）にあり、規模の下限が要りません。**初日から出ます。**

```
metrics.skillFired  →  { numerator: 3, denominator: 27 }
metrics.mcpUsed     →  { numerator: 4, denominator: 10 }
```

読み方は「**書いたスキル 27 個のうち、実際に発火したのは 3 個**」「繋いだ MCP 10 個のうち
呼ばれたのは 4 個」。

**残り 24 個のスキルは、毎セッション文脈を消費しながら一度も仕事をしていません。**

これは点数と違って、そのまま行動になります。使っていないスキルを消す、呼ばれていない
MCP を切る。**原因の推測ではなく在庫の事実**なので、断定して構いません。

`axes` の `safetyCheck` にも近い数字が入っています（`skillsDefined` / `hooksDefined` /
権限の内訳）。こちらも採点されませんが、必ず出ます。

---

## 8. `composite` — 総合点

```
composite  56.9 (B) over 4 axes, outcome 57.56 — leans mixed (both directions, so neither can be told)
```

**総合点は内訳の「後」に出ます。** 1 つの数字を先頭に置かないのは意図的です。

| 段 | 範囲 |
|---|---|
| **S** | 85 以上 |
| **A** | 70 以上 |
| **B** | 55 以上 |
| **C** | 40 以上 |
| **D** | 40 未満 |

- **`outcome` / `design`** — 結果側（空振り・自己検証・定着）と設計側（代謝・再発防止）の内訳。それぞれ本数が揃ったときだけ出ます
- **`leans`** — 落とした項があるとき、**総合点がどちらへずれているか**。`mixed` は「両方向に落ちているので、どちらとも言えない」です

**`leans` が付いた点は、正しい点ではありません。** ずれの向きが分かる点です。この 2 つを混同しないでください。

`composite none — <理由>` は、総合点を出さないと決めた状態です。

---

## 9. `validation` — 出力そのものの検査

```
validation passed (0 violations, 1 flags)
           W-1 scanManifest.originFieldCoverage: 2.8% — origin coverage under 10% ...
```

- **`violations`** — 出力が信用できない。**ゼロでなければならない項目**です
- **`flags`** — 警告。出ていて構いませんが、読んでください

**これは受け取り側のコードと同じものです。** マニフェストの無いペイロードや、定義の食い違うペイロードは、送る側の規律ではなく**受け取る側の拒否**で止めます。設計期間 2 日で 4 件の定義事故が起き、うち 2 件は「定義を明示せよ」と書いた本人が直後に破ったからです。

---

## 10. いつ役に立ち始めるか

| 経過 | 使えるもの |
|---|---|
| 初回 | `by version` と資産の内訳（規模不問）。点は 4 軸ぶん。**比較はまだ無い** |
| 2 回目〜 | 前回との差（ただし「変化」とは呼ばれない） |
| **窓 1 本ぶん（約 2 週間）** | `recurrencePrevention` が本当に再発を測り始める |
| それ以降 | 時系列。**このツールが本来やろうとしていること** |

**焦って毎日何度も回しても、窓は動きません。** 1 日 1 回で十分です。

---

## 11. よくある誤読

**「点が低いから環境が悪い」** — 違います。点は他人と比べられません。**先週の自分**とだけ比べてください。

**「`0/11` だから測れていない」** — 違います。0 は測れた結果です。測れなかったときは、その旨が理由付きで出ます。

**「差が `+1.2` だから改善した」** — 違います。区間が無いうちは、どの差も変化と呼べません。

**「`not_applicable` はバグ」** — 違います。**数字を出さないと決めた場所**です。理由が必ず添えてあります。
