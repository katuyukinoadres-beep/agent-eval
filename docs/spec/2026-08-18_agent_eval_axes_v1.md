# AIエージェント性能評価ダッシュボード 測定軸 設計書 v1

作成日: 2026-08-18
対象: 個人が使っている AI エージェント環境（Claude Code / Codex / Cursor 等）を採点し、総合評価・母集団内の位置・エージェント側の直し方・人間側の渡し方を返す製品の測定軸

前提となる確定方針（変更しない）
- トークン量・支出額では競わせない。測るのは質
- ローカル解析で完結し、外部へ送るのはスコアと分類ラベルのみ（opt-in）
- 赤の他人の環境でも同じ式で測れること。特定個人の環境専用の指標は採用しない
- 偏差値は分母が育つまで名乗らない

このv1は、統合案8軸に対して3レンズ（悪意あるユーザー / 実装者 / 懐疑的ユーザー）から入った反証を反映した結果である。統合案からの主な変更は次の4点。

1. 「ガードレール実効度」を採点軸から外し、非採点の安全チェックに降格した（静的ファイルの穴埋め問題になっていた）
2. 「監督バランス」を解体し、人を採点しない「手離れ度」に作り直した
3. 「学習定着率」を、実測で分子が1件しか出ない閉鎖率ベースから、窓を跨いだ同一署名の再出現ベース（再発防止率）に組み替えた
4. 新しく「成果の定着」を追加した。8軸すべてが手順しか見ておらず、きれいな手順でゴミを量産している人が満点を取れる穴を塞ぐため

## 1. 1枚サマリ

### 採点する8軸

| # | 軸名 | 側 | 一言でいうと | 重み | 実現性 |
|---|---|---|---|---|---|
| 1 | 一発着地率 | エージェント | 1つの成果物に着地するまで何回書き直したか。そのうち人間の差し戻しが原因なのは何割か | 15 | 高 |
| 2 | 空振り率 | エージェント | 到達に寄与しなかった手数を、1タスクあたり何回踏んだか | 14 | 高 |
| 3 | 自己検証率 | エージェント | 出したものを自分で確かめてから返しているか。失敗を人間を呼ばずに立て直せるか | 14 | 中 |
| 4 | 成果の定着 | 成果 | 作ったものが後で実際に使われたか。手ぶらで終わった依頼はどれくらいあるか | 14 | 中 |
| 5 | 環境の代謝 | エージェント | 毎回払っている固定コンテキスト税に見合う資産だけが残っていて、実際に発火しているか | 10 | 高 |
| 6 | 再発防止率 | 両方 | 先月と同じ失敗・同じ指摘がまだ出ているか | 13 | 中 |
| 7 | 依頼の設計度 | 人間 | 依頼の起点に、対象・制約・完成条件が入っているか | 12 | 中 |
| 8 | 手離れ度 | 人間 | 成果1件に、どれだけ発話と時間を張り付かせたか（自己時系列のみ） | 8 | 中 |

### 採点しないが必ず出す2つ

| 名前 | 何をするか |
|---|---|
| 軸0: 測定カバレッジと観測整合性ゲート | 何日分を読めたか / 何行パースできなかったか / 何セッションを除外したか / ログが改変されていないか。整合性が閾値を割ったら総合点そのものを出さない |
| 安全チェック（旧ガードレール軸） | 「設定しているつもりで壊れている」3つだけを実名で警告する。順位は付けない |

読み方の原則
- 総合点は出すが、単一の数字に潰さない。〈帰結スコア（軸1・2・3・4）〉×〈設計スコア（軸5・6・7・8）〉の2次元も必ず併示する
- 2回目以降は各軸の前窓比Δを主表示にする。ただし信頼区間が重なるΔは「変化なし」と表示する
- 人間側2軸（軸7・軸8）は人の優劣ではなく接し方の癖として返す。改善アドバイスの主語は常にエージェント側に置く

## 2. 全軸に効く共通の土台

ここを外すと、どの軸の式も成立しない。

### P1. 人間の生発話の切り出し

`type == "user"` かつ `isSidechain != true` を取り、次を除外する。

- content 配列に `tool_result` ブロックがあるもの（実測 1,990件中 1,712件がこれ）
- 本文先頭300字に `<command-name>` `<command-message>` `<local-command-stdout>` `<local-command-caveat>` `<system-reminder>` を含むもの
- 先頭200字が `Base directory for this skill:` のもの（スキル注入）
- `[Request interrupted by user]` 系（別カウントして除外）

`origin.kind == "human"` は、実測で text メッセージ144件中134件でキー自体が欠落していた。あれば使う補助条件に留め、「無い＝人間でない」とは読まない。

### P2. 自動起動セッションの除外

次のいずれかに該当するセッションを人間側評価の母集団から外す。

- 初回発話が `<system_instructions>` / `You are a subagent` 型
- 初回発話が他セッションと完全一致
- 人間発話が1件のみで、かつ極端に長い

実測ではこの環境の1,108セッション中、除外できたのは190件だった。統合案が前提にしていた934件（85%）には届かない。よって「除外しきれる」前提の設計は置かない。除外できなかった自動セッションが残ることを前提に、人間側2軸には最小分母を必ず持たせる。

除外したセッション数そのものは「自動化の厚み」として参考表示する（採点しない）。

### P3. 環境ノイズの除外

`isApiErrorMessage` / `model == "<synthetic>"` / `system.subtype == "api_error"` を全軸の分子分母から外す。回線不調を低品質と誤判定しないため。

### P4. 窓スナップショット

`cleanupPeriodDays` で生データは消える（実測でちょうど14日前で切れていた）。毎回 `~/.agentscore/snapshots/` に次を書き出す。本文は保存しない。

- 8軸の分子分母を分けた生の中間値
- 署名ハッシュ集合（エラー署名 / 誘発パス / 人間指摘クラスタ）
- 直前スナップショットのハッシュを含める（hash chain）

指標定義を後から変えると過去が再現できないため、8軸すべてを初回から同時に記録する。

### P5. タスク束の定義

`parentUuid` チェーンで、1つの人間発話から次の人間発話までを1タスク束とする。人間発話が1件しかないセッションが実測 945/1,108 あるため、束が1つしかないケースを前提に含める。

### P6. 確定成果物 SA の定義（軸1・軸4・軸8の共通分母）

反証で最も強く叩かれた定義なので、次のように硬化した。

```
SA(p) が成立する条件:
  p は Edit / Write / NotebookEdit の file_path である
  かつ p への最後の書込が「窓の最終3日より前」（右打ち切り。統合案の7日から短縮）
  かつ os.path.exists(p) が真         # 存在確認だけ。中身は読まない
  ※「以後再編集なし」という条件は撤廃した
```

統合案は「以後再編集されていない」を SA の条件にしていたが、実測では編集された1,498パスのうち2セッション以上にまたがって再編集されたのは135件（9.0%）しかない。つまり残り91%は「一度書いて二度と触っていないファイル」で、長期に手入れし続けているファイルほど分母から消える逆相関が起きていた。再編集の有無は分子（深度）だけで扱う。

重み付けには「受領シグナル」を掛ける。書いて放置しただけの水増しを、成果として満額で数えないため。

```
uptake(p) = 1.0  # 次のいずれかを満たす
            #  (a) 書込より後の tool_use の引数 / 人間発話 / 他ファイルの参照に p が現れた
            #  (b) 次窓でも p が存在し続けた
            #  (c) p を引数にした実行が成功した
          = 0.4  # どれも満たさない

w(p) = clip(1 + log10(窓内に p へ書かれた累計 newLines / 50), 0.5, 3.0) * uptake(p)
```

重みの根拠に「ファイルの最終文字数」を使わないのは、ディスクからの本文読み取りを全廃するため。実測で編集対象1,498パスのうち138件はプロジェクト外（業務機密の本体）にあった。存在確認だけならプライバシー方針と衝突しない。

同一タスク束・同一親ディレクトリ・同一拡張子・サイズ差2倍以内は1クラスタ＝1件に丸め、束あたり最大3件でクリップする。

### P7. 用途プロファイルの判定（軸3・軸7・コホート分けに使う）

編集拡張子分布とツール分布から、コード / 文書 / 調査 / 混在 を機械判定する。実測のこの環境は `.py 867 / .md 420 / .html 151 / .txt 49` で「コードと文書の混在」型。

判定結果は次の3つに使う。
- 軸3の検証型の切り替え
- 軸7の母集団平均の表示可否
- 母集団比較のコホート分け

用途差を欠測だけで吸収すると、欠測が増えるほど残り軸の重みが跳ね上がってノイズが増幅する。先に用途を判定してから軸を当てる。

### P8. イベントから軸への帰属表（二重計上の防止）

同じ1イベントが複数軸に出る箇所は、帰属先を1つに固定する。

| イベント | 帰属先 | 他軸での扱い |
|---|---|---|
| `PreToolUse:* hook error` を含む tool_result（実測29件） | 安全チェック（作動証拠） | 軸2の分子分母から除外 |
| `toolDenialKind == "permission-rule"`（実測40件） | 安全チェック | 軸2・軸8では内訳表示のみ |
| `toolDenialKind == "user-rejected"`（実測11件） | 軸8の内訳表示（採点しない） | 他軸では使わない |
| 軸3が検証としてカウントした tool_use_id | 軸3 | 軸2の反復分子から除外 |
| `[Request interrupted by user]`（生成中断・実測20件） | 軸1の誘発判定 | 軸8では内訳表示のみ |
| `[Request interrupted by user for tool use]`（ツール中断・実測11件） | 安全チェック | 採点しない |

## 3. 軸0（ゲート）測定カバレッジと観測整合性

採点しない。総合点を出してよいかどうかを決める門番であり、レポートの冒頭に必ず置く。

### 問い
そもそも何をどれだけ読めたのか。読んだログは書き換えられていないか。測定の直前だけ環境が整えられていないか。

### なぜ軸より先に要るか
8軸すべてが、ユーザーが完全な書き込み権限を持つ平文ファイル（`*.jsonl` / `~/.claude.json` / `settings*.json`）だけを読む。しかも設計はスキーマ変動に備えてフィールド欠損に耐える実装にする方針で、これは偽レコードを弾かないことと同義である。加えて `cleanupPeriodDays` で原本が消えるため、後から真正性を検証する手段がない。母集団比較を始める前にここを塞がないと、初日に最上位が全部合成ログになる。

### 出力A: カバレッジ（スコアと同格でレポート冒頭に出す）

- 実効窓日数（環境ごとに 0 / 14 / 30 / 無期限と違う。実測のこの環境は14日）
- 読んだファイル数・行数・パース失敗行数
- 除外したセッション数と理由別内訳（tool_result / システム注入 / 自動起動 / API エラー）
- 欠測になった軸の一覧と、その理由
- サブエージェント配下（`<sessionId>/subagents/` `<sessionId>/workflows/`。実測45個）を join したか、していないなら除外率

これを出さないと、スコアが低いのか測れなかったのかをユーザーが区別できない。

### 出力B: 観測整合性スコア（0-100・ゲート判定に使う）

6項目の合成。

```
I1 uuid / parentUuid チェーンの欠損率（親が存在しないレコードの割合）
I2 timestamp の単調性違反率、およびミリ秒下位桁の分布の自然さ
I3 usage 値の連続性（同一セッション内で cache_read が不連続に飛んでいないか）
   とモデル別トークン単価との整合
I4 file-history の実バイト列と structuredPatch の一致率
   ※ file-history のバックアップ実体は実測でセッションの13%にしか残っていないため、
     残っている分だけを検査する（不在は減点しない）
I5 jsonl ファイルの mtime と最終レコード timestamp の整合
I6 前窓スナップショットの hash chain の連続性
```

### 出力C: 測定直前の環境改変の検出

`settings*.json` / `CLAUDE.md` / `.claude/skills/` / hook スクリプトの mtime を窓内の位置と突き合わせ、次を検出する。

- 設定ファイルの mtime が窓の後半20%に集中している
- 各軸の値が窓の前半と後半で急変している（依頼の設計度が後半だけ上昇、hook が後半にだけ出現、bypassPermissions が後半だけ消える 等）

該当した場合、「測定の直前に環境が変わっています」と明示し、静的な要素を含む軸（軸5・安全チェック）に減衰係数を掛ける。

### ゲート判定

| 状態 | 挙動 |
|---|---|
| 整合性スコア 85以上 かつ 実効窓日数 7以上 | 総合点・Tier ともに出す |
| 整合性スコア 60-85 | 総合点は出すが「観測に不整合あり」を併記し、percentile 参加は不可 |
| 整合性スコア 60未満 または パース失敗率 5%超 | 総合点・Tier を出さない。カバレッジと軸別の内訳だけ返す |

percentile への参加資格は、軸0通過に加えて「連続2窓以上の hash chain 保持」を条件にする。chain のハッシュだけをサーバに預ける（本文は送らない）。過去を書き換えると chain が壊れ、参加資格を失う。

## 4. 軸1 一発着地率（First-Pass Landing）／ エージェント側 / 重み15

### 問い
1つの成果物に着地するまで、何回書き直したか。そのうち、人間の差し戻しが原因なのは何割か。

### データ源
- `tool_use.input.file_path`（Edit / Write / NotebookEdit）
- `toolUseResult.structuredPatch[{oldLines, newLines, lines[]}]` と `toolUseResult.originalFile`
- 人間発話の位置（制御が人間に戻った点）
- `[Request interrupted by user]` のタイムスタンプ
- SA の存在確認（`os.path.exists` のみ。本文は読まない）

file-history の `version` は主源から外した。実測で version はセッション単位でリセットされ、`memory/pending_actions.md` は113セッションに分散して各セッションの max が [15, 15, 13, 10, 9, ...] だった。窓内の max を取ると「最も長く粘った1セッション」しか測れず、30セッションに分けて2回ずつ直した60編集が満点になる。セッションを分けるだけで満点になる指標は使えない。

### 算出式

```
# 深度: セッションを跨いで自前集計する
depth(p) = 窓内で p に対して発行された Edit/Write/NotebookEdit 呼び出しの総数

# 誘発型の分離: 否定語辞書を使わず、行動で判定する
induced(p) = p への再書込のうち、直前に「人間発話1件」を挟んでいるものの回数
             ※「直前」= 同一セッション内で直近の人間発話1件。それ以前には遡らない
I = Σ induced(p) / Σ (depth(p) - 1)
    ※ 分母が10未満なら I は欠測（係数分の減点をしない）

# 修正の大きさ
M = median( (追加行 + 削除行) / originalFile の行数 )
    ※ structuredPatch が空配列のもの（実測4,090件中1,225件＝30%）は
      「新規作成」として別カテゴリに分け、M の計算から外す

score = 100
      - 4  * max(0, p90(depth) - 3)
      - 30 * I                        # I が欠測なら項ごと落として重みを再配分
      - 8  * [M > 0.5]
      - 2  * max(0, median(depth) - 2)
     を 0-100 にクリップ
```

統合案からの係数変更
- p90 の係数を 12 から 4 に落とした。長文の記事や議事録を段階的に組み立てて p90=8 になった人が、それだけで60点失う設計だった。コードは小さい差分の積み上げで深度が伸びにくく、文書は伸びる。用途間の不公平が大きすぎる
- 誘発比率の係数を 60 から 30 に落とし、最小分母10を課した。分母が2で片方が誘発なら I=0.5 で30点動くのは乱数と変わらない
- 誘発判定から否定語辞書を外した。「違う」を「もう一段いこうか」と言い換えるだけで係数が丸ごと消えるのは最も安いハックだった。辞書は表示上の分類にのみ使う

### 採点方法
0-100。Tier: 85以上 S / 70-85 A / 55-70 B / 40-55 C / 40未満 D。

表示は必ず〈深度 p90 / 誘発比率 I / 全書き換え比 M〉の3内訳と、深度10超の成果物をパス付きで実名列挙する。スコアより実名列挙のほうが行動を変える。

SA が0件の環境（相談・調査のみ）は本軸を欠測とし「対話中心」ラベルを付けて総合点の分母から外す。

### 初回計測時の扱い
初回から算出できる。2回目以降は p90 と I の前窓差分を並記する。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| file-history を通らない経路（リダイレクト、`sed -i`、`cp`、ビルドスクリプト、外部エディタ）で書いて深度を増やさない | コマンド文字列のパースをやめ、ファイルシステムで実測する。窓の開始と終了で対象ディレクトリの (path, mtime, size, ハッシュ) を取り、書込ツールに一度も現れていないのに窓内で変化したファイルを直接数える。この比率が高い環境は本軸を欠測にして警告する。`python build.py` の中の `open().write()` はコマンド文字列に現れないので、文字列パースでは必ず破られる |
| 毎回別名の新規ファイルで作り、深度を1に保つ | 同一ディレクトリ・同一拡張子で連番/日付サフィックスの新規パスが窓内に3件以上出たら回避パターンとして検出（旧版バイト列に依存しない。file-history のバックアップ実体はセッションの13%にしか残っていない） |
| 中身の薄いファイルを量産して SA を水増しする | 受領シグナル（P6の uptake）で 0.4 に減衰、log重み、クラスタ丸め、束あたり3件クリップの4重。量産すると軸4の再参照率が同時に落ちる |
| 1回で完璧に書く | 防御不要。望ましい行動そのもの |

### 低スコア時のアドバイス（文面例）

例1（誘発比率が高い＝人間起因）
「深度の p90 が8回、うち41%があなたの差し戻しの直後に起きています。着手前に、見出しと各節1行だけを出させて、その骨子にOKを出してから本文を書かせてください。同じ作業で深度は2〜3に落ちます。最も書き直されたのは output/Ujjwal会議_手元メモ.md（14回）です。」

例2（誘発比率が低く深度だけ高い＝エージェント起因）
「書き直しの82%が、あなたが何も言っていない間に起きています。エージェントが自分で迷っている状態です。この種類の成果物について『何を・何字で・どの構造で出すか』がスキルにもCLAUDE.mdにも定義されていません。出力の形を1つ決めて書いてください。」

## 5. 軸2 空振り率（Wasted Motion）／ エージェント側 / 重み14

### 問い
到達に寄与しなかった手数を、1タスクあたり何回踏んだか。

窓を跨いだ再発（同じ失敗をまだ踏んでいるか）は軸6に移した。本軸は窓内だけを見る。

### データ源
- `tool_result{is_error, content}` を `tool_use_id` で join したツール名（実測 18,241呼び出し / 491エラー = 2.69%）
- Bash / PowerShell の `toolUseResult{timedOutAfterMs, persistedOutputSize}` と content 先頭の `Exit code N`
- Grep の `Ripgrep search timed out`
- `tool_use.input` の正規化ハッシュ

### 算出式

```
# 分子（1タスク束あたりの空振り手数）
分子 = 1.0 * 失敗呼び出し数
     + 0.7 * 書込/実行系の反復（同一タスク束で (tool_name, 正規化input) が2回目以降）
     + 0.2 * 調査系の反復（Read / Grep / WebSearch / WebFetch の同上）
     + 1.0 * timedOutAfterMs 付き呼び出し
     + 0.5 * persistedOutputSize > 100KB の呼び出し
     + 0.5 * 成功したが到達に寄与しなかった呼び出し
              ※ その tool_result の内容が、以後の tool_use の input / 編集内容 /
                応答文のどこにも現れなかったもの

# 除外
  - hook 起因の失敗（`PreToolUse:*` `PostToolUse:*` を含む tool_result。実測29件）は
    分子・分母とも除外し、安全チェックへ回す
  - 軸3が検証としてカウントした tool_use_id は反復分子から除外
  - ユーザー自作スクリプト由来の Traceback（command の第1トークンが python / node で、
    引数が窓内で既存パスを指すもの）は重み 0.3 に減衰

# 分母
分母 = タスク束数
       ※ 束あたり呼び出し数は母集団 p90 で winsorize する

W = 分子 / 分母   # 1タスクあたり空振り手数

# 窓内再発
sig = (tool_name, error_class, target_kind)
  error_class は決定的な正規表現で分類:
    edit_string_not_found / edit_stale_read / cmd_not_found(exit 127) /
    traceback:<例外クラス> / timeout / permission_denied / no_such_file /
    syntax_error / other:<content先頭60字のhash>
  target_kind は拡張子またはコマンド第1トークン（いずれもソルト付きハッシュ化）
r_in = 1 - distinct(sig) / count(errors)

score = 100 * (1 - 0.65 * min(1, W / W_ref) - 0.35 * r_in)
```

W_ref（正規化定数）は暫定で 3.0（1タスクあたり3手の空振りで満点減点）とするが、母集団が貯まるまでは絶対値を他人と比較しない。初回リリースでは自分の前窓比と、分類別の実名上位3件だけを出す。

統合案からの変更
- 分母を「総ツール呼び出し数」からタスク束数に変えた。総呼び出し数を分母にすると、失敗を減らすより確実に成功する呼び出しを数百回打って分母を膨らませるほうが安く、しかも副作用がゼロだった
- 「成功したが到達に寄与しなかった呼び出し」を分子に入れた。これで無意味な操作の量産が加点ではなく減点に反転する
- 反復加点を調査系（0.2）と書込/実行系（0.7）に分けた。Grep を条件を変えて何度も打つ、同じ資料を読み返すのは調査の作法であって空振りではない
- 窓跨ぎ持越率 r_cross を軸6へ移した

### 採点方法
0-100。Tier: 85以上 S / 70-85 A / 55-70 B / 40-55 C / 40未満 D。

必ず4分類の内訳を出す。
- (a) 思い込み編集: `String to replace not found` / `File has been modified since read`（実測 23件 / 16件）
- (b) 環境理解不足: exit 127 / `No such file` / SyntaxError
- (c) 設計の粗さ: timeout / 巨大出力（Grep のタイムアウト実測17件）
- (d) 権限ズレ: permission denied

フィルタ後のツール呼び出しが窓内50未満の環境は欠測（何もしない満点を成立させない）。

### 初回計測時の扱い
初回から算出できる。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| 分母を膨らませる（確実に成功する呼び出しを大量に打つ） | 分母をタスク束数に変更済み。加えて「寄与しなかった成功呼び出し」が分子に入るので、打つほど下がる |
| 失敗を握り潰す（エラー抑制、または全コマンドを1本のラッパー経由にする） | 文字列検出をやめ、分布で検出する。exit 0 率が母集団の上位0.1%に張り付く / stdout が空か極小の呼び出し比率が異常 / 単一ラッパー経由の呼び出しが全体の大半、のいずれかに該当した環境は本軸を欠測にして「失敗が見えていない可能性」を明示する。減衰係数は掛けない（エラー抑制記法は Windows 環境の定型でもあり、書き癖を減点にしない） |
| エラー文言を握り潰して署名を変える | tool_name と target_kind の組は変わらないので同型判定は生き残る |
| ツールを使わず手で書く | 分母も減るので比率は動かず、呼び出し50未満で欠測 |

### 低スコア時のアドバイス（文面例）

例1
「Edit の失敗39件のうち23件が『String to replace not found』でした。編集前にファイルを読んでいません。散文のルールはあなたの環境でも守られていないので、PreToolUse の Edit フックで『直前に同じパスの Read があるか』を検査してブロックしてください。」

例2
「Grep のタイムアウトが17件。すべて対象ディレクトリを指定しない全走査でした。CLAUDE.md に『Grep は既定で src/ と .claude/ に絞る』の1行を入れると消えます。あわせて exit 127 が9件あり、これはこのマシンに存在しないコマンドを組み立てた回数です。OS・シェル・使えるCLI を3行だけ先頭に置いてください。」

## 6. 軸3 自己検証率（Self-Verification）／ エージェント側 / 重み14

### 問い
出したものを自分で確かめてから人間に返しているか。失敗したとき、人間を呼ばずに立て直せるか。

外部の実測で、明示的な自己検証は成功確率を13〜87%押し上げ、自己修正は成功率を1.5〜4倍にする。効果量の裏付けがある数少ない行動指標なので重みを厚くしている。

### データ源
- tool_use の並び（name と input.file_path / input.command）
- tool_result.is_error
- 書き込み系ツールの file_path
- 過去窓スナップショットに記録した「非ゼロ終了したことのあるコマンド」の集合

### 算出式

```
# 区間の切り方（人間発話で区切らない）
編集区間 = 「ある file_path への書込」から「同じ file_path への次の書込 または セッション終了」まで
  ※ 実測で人間発話が1件だけのセッションが 945/1,108 ある。人間発話で区切ると
    大半のセッションが1区間に潰れて分母が1になる

# 検証アクション（コマンド辞書を使わない）
検証と認める条件は、次のすべてを満たすこと:
  (i)  編集した file_path、またはその親ディレクトリが、
       Read の対象 / Grep の対象 / Bash・PowerShell の引数のいずれかに現れる
  (ii) 実行系の場合、そのコマンド（第1トークン + 主要引数の形）が
       過去窓で少なくとも1回は非ゼロ終了したことがある
       → 常に通る飾りコマンドは検証として数えない
  カウントは1編集につき1回まで。結果を参照しない連続 Read は3件以上でも1件に丸める

V = 検証ありの編集区間 / 全編集区間

# 検証が機能した証拠（飾りの検証を満額にしない）
G = 検証アクションのうち「非ゼロ終了 → それを受けた編集」の連鎖が起きた割合
V_eff = V * (0.7 + 0.3 * min(1, G / 0.2))

# 自己修復率
S = 失敗のうち、人間発話を挟まずに同じ対象で3回以内に成功へ転じた割合
    ※ 分子は「そのセッションで初出のエラークラス」に限る
      （直前に自分で作った失敗からの回復は除外する）
    ※ 人間発話を挟んで解決したものは分子に入れないが、減点もしない。
      〈自己修復 / 人間救援 / 未解決〉の3分割で内訳表示し、減点は未解決だけ

score = 100 * (0.60 * V_eff + 0.30 * S + 0.10 * (1 - 未解決率))
        - 5 * [TodoWrite 未使用]
```

統合案からの変更
- コマンド辞書（test / pytest / npm / python / node など）を全廃した。実測でこの環境の Bash 呼び出し7,922件の大半が python 実行形式で、編集の後に来る次の作業（メール送信・vault保存）が全部「実行系検証」として重み1.0で数えられていた。逆に辞書に無い言語圏・非開発用途では実行系が常時ゼロになる。二値で失敗する
- 実行系ゼロで70点キャップという制限を撤廃した。議事録・記事・メール下書きに「1コマンドで通る検証」は原理的に存在しない。秘書業務や執筆を主用途にする人が、どれだけ丁寧でも永久にC相当で天井に張り付く設計だった。代わりに用途プロファイル（P7）別に検証の型を定義する
  - コード: 編集パスを引数に含む実行
  - 文書: 書き戻し Read + 同一パス Grep + 出力前の自己読み返し
  - データ: 件数照合の実行
- TodoWrite の pending 率を重み付き減点にするのをやめ、固定の小減点にした。減点項だけを持つ項目は「使わない」が最適戦略になる
- 自己修復率の分子を初出エラークラスに限定した。確実に失敗するコマンドと確実に成功するコマンドを並べるだけで S が 1.0 になる自作自演を封じる

### 採点方法
0-100。Tier: V_eff 0.5以上 かつ S 0.6以上 で S、V_eff 0.15未満は D（書きっぱなし）。

V と S は必ず内訳表示する（V が低く S が高い＝失敗してからは直すが、失敗しなければ確認しない）。編集区間が窓内25未満なら欠測。統合案の10では、10〜20の帯で Tier 境界をまたぐのが1〜2区間の差になる。

### 初回計測時の扱い
初回から算出できる。ただし条件(ii)の「過去窓で非ゼロ終了したことがある」は初回に判定できないため、初回のみ条件(ii)を外し、その旨を明示する。2回目以降から本判定になる。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| PostToolUse フックに常に成功する1行コマンドを仕込んで全編集で V=1.0 を恒久化する（統合案では、この行動が製品自身のアドバイス文と一字一句一致していた） | 条件(ii)で封じる。過去窓で一度も失敗したことのないコマンドは検証として数えない。加えて G（検証が機能した連鎖）で満額にしない |
| 編集のたびに意味のない Read を差し込む | 編集した file_path と一致するもののみ、1編集1回まで、空 Read は丸め。残る水増し余地（書いた直後に読み戻す）は推奨行動そのものなので、ハックの手順と正しい行動が一致する設計として許容する |
| 自作自演の失敗から修復して S を稼ぐ | 分子を初出エラークラスに限定 |
| TodoWrite を使わずに減点項を消す | 未使用は固定の小減点にした |

### 低スコア時のアドバイス（文面例）

例1（コード用途）
「編集1,332回のうち、書いた対象を自分で確かめたのは12%。実行系の検証は窓内0件でした。CLAUDE.md に『編集したら確認する』と書く方式は、あなたの環境では守られていません。PostToolUse の Edit フックで1コマンドの検査を自動実行に変えてください。検証コマンドが1本もない場合は、まず『1コマンドで通る検査』を1本作るのが最優先です。」

例2（文書用途）
「議事録と記事が主な成果物なので、実行系の検証は求めていません。ただし『書いた直後に自分で読み戻す』が編集区間の9%でしか起きていません。出力契約に『保存したら最終版を読み直し、参加者名と決定事項の件数を数えて報告する』の1行を入れてください。あわせて、失敗の61%をあなたが救っています。『同じ手を2回繰り返さない。1回失敗したら別経路で引き直してから報告する』をIF-THEN形式で入れると、この61%が下がります。」

## 7. 軸4 成果の定着（Artifact Uptake）／ 成果側 / 重み14

新規追加。3レンズのうち2つが同じ穴を指摘した。8軸すべてが手順しか見ておらず、きれいな手順でゴミを量産している人が満点を取れる。加えて、無言で閉じた不成立セッションが従来の設計では単に欠測になり、失敗が一切減点されなかった。

### 問い
作ったものは、後で実際に使われたか。手ぶらで終わった依頼はどれくらいあるか。

### データ源
- SA（P6）と、その後の tool_use.input / 人間発話 / 他ファイルの参照に同じパスが現れるか
- 前窓スナップショットに記録した SA パスの集合（次窓生存の判定）
- attachment.type == "edited_text_file" と toolUseResult.staleRecovered（実測12件）
- タスク束ごとの成果物の有無と、束末尾の人間発話の性質

### 算出式

```
# (a) 再参照率
R = Σ w(p) * [ p が書込後に再登場した ] / Σ w(p)
    再登場と認めるもの:
      - 書込より後の「別タスク束」の tool_use の input
        （Read / Grep / Bash の引数 / 他ファイルの参照）に p が現れた
      - 書込より後の人間発話に p が現れた
      - 次窓のスナップショットに p が存在し続けた
      - p を引数にした実行が成功終了した

# (b) 放棄率
A = 放棄タスク束 / 全タスク束
    放棄 = その束で書込ツールが1回も成功せず、かつ束末尾の人間発話が
          肯定 ack でもなく、次の束が同じ話題の続きでもないもの
    ※ 束が1つしかないセッション（実測 945/1,108）も対象に含める

# (c) 人手上書き率
O = 人が手で直した痕跡のある SA / SA
    痕跡 = edited_text_file が同一パスに出た、または staleRecovered == true

score = 100 * (0.55 * R + 0.30 * (1 - A) + 0.15 * (1 - O))
```

### 採点方法
0-100。Tier: 80以上 Landed / 60-80 Mostly landed / 40-60 Loose / 40未満 Scattered。

必ず「再参照されなかった SA」を実名で上位5件出す。これがそのまま棚卸しリストになる。

SA が0件、またはタスク束が窓内10未満の環境は欠測。

### 初回計測時の扱い
初回でも (a) の再参照（窓内での再登場）、(b) 放棄率、(c) 人手上書き率は出る。次窓生存だけが2窓目からになるので、初回は再参照の判定条件から次窓生存を外し、その旨を明示する。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| 自分の書いたファイルを毎回 Read して再参照率を稼ぐ | 再参照は「書込より後の別タスク束で」現れたものに限る。同一束内の書き戻しは軸3の検証としてカウント済みで、本軸では数えない。空 Read の水増しは軸2の反復分子で相殺される |
| 放棄セッションの記録を消す | 軸0の hash chain と、束数の窓間の急減で検出する |
| 成果物を出さずに済む依頼だけをする | 束数が10未満で欠測になり、順位は上がらない |
| 中身の薄いファイルを大量に作る | w(p) の log 重みとクラスタ丸め。薄いファイルは再参照されないので R が落ちる |

正面から点を上げる唯一の経路は「後で使うものを作る」「途中で投げ出さない」であり、どちらも実際の改善行動である。

### 低スコア時のアドバイス（文面例）

例1
「窓内に確定した成果物42件のうち、後で一度でも読み返されたのは11件（26%）でした。使われなかったものの上位は output/調査_パッチECG_v3.md、output/tmp_summary.md、scratch/note.md です。同じ内容が別ファイルに3回作り直されている形跡があります。作る前に『この結果をどこに置くか』を1つ決めて、既存ファイルへの追記に切り替えてください。」

例2
「人間が指示を出したのに成果物が何も残らず終わった依頼が、窓内で18%ありました。うち9件は『調べて』で始まり、調べた結果がどこにも保存されていません。調査系の依頼に『結果は docs/research/ に1ファイルで残す』を既定として付けると、次の窓で同じ調査を繰り返さずに済みます。」

## 8. 軸5 環境の代謝（Environment Metabolism）／ エージェント側 / 重み10

### 問い
毎回払っている固定のコンテキスト税に見合う資産だけが残っているか。作った資産は実際に発火しているか。

### データ源
- 実測の入力トークン: message.usage.input_tokens + cache_read_input_tokens + cache_creation_input_tokens
- 静的: 全スコープの CLAUDE.md と @import 再帰先の文字数（内訳表示用）
- skill_listing attachment の content（実測398件・中央値 6,452字・最大 20,001字）
- attributionSkill（実測41種）
- hook_success / hook_additional_context / mcp_instructions_delta の content 文字数
- tool_use.name の MCP ツール呼び出しの出現

### 算出式

```
# 文脈税 FC（静的な文字数ではなく、実際に払っているトークンで測る）
FC = median( 1タスク束あたりの実効入力トークン )
   = median( usage.input_tokens + cache_read_input_tokens )

台形スコア:
  FC <=  40k tokens         : 100点
  40k < FC <= 120k tokens   : 超過 20k ごとに -8点
  FC > 120k tokens          : 下限 20点
  FC が小さい側の減点は行わない（Thin ラベルの表示のみ）

# 稼働率 U
資産集合 = 窓内の skill_listing に実際に載ったスキル名
         ∪ 窓内に発火記録のあるイベントに登録された hook
         ∪ settings / .mcp.json のマージ結果で有効化された MCP サーバ
U = Σ 資産ごとの発火重み / 資産数
  発火重み: attributionSkill / hook_success の hookName / MCP ツール呼び出しの出現回数で
            0回 → 0 / 1回 → 0.3 / 2-4回 → 0.7 / 5回以上 → 1.0
  ※ 資産数が3未満なら U は欠測

# 死蔵税
Wd = 未発火スキルの description 文字数合計 / skill_listing の総文字数
     Wd > 0.3 で -10

# 静的欠陥（ベンダー一次情報の数値基準のみを根拠にする）
D = 違反率 * 15
    違反項目: SKILL.md が500行超 / description が空または1024字超 /
             参照が2階層以上ネスト / 100行超の reference に目次がない

score = 台形スコア * (0.5 + 0.5 * U) - Wd - D   を 0-100 にクリップ
```

統合案からの変更
- FC の主指標を、静的な常時ロード文字数から「1タスク束あたりの実効入力トークンの中央値」に変えた。静的な文字数で測ると、CLAUDE.md に「作業前に必ず docs/context.md を読め」と1行書いて実体をそちらに移すだけで税が消える。経路を1本ずつ塞ぐ方式は必ず別経路で回避される。実測トークンなら経路を問わず実際に払っている分が乗る。静的な文字数（この環境で CLAUDE.md 11,912字 + rules 31,713字 = 43,625字）は内訳表示に降格する
- 文字数の下限側の減点を撤廃した。「指示書が薄いと質が落ちる」は実証されていない。401リポジトリ・1,876ファイルを調べた研究は「ルールが LLM 性能を上げる証拠は無い、開発者の直感に基づく」と明記している。実害が実証されていないものを60点分の減点にはできない
- U の分母を「ディスク上の定義数」から「skill_listing に実際に載った集合」に変えた。ディスク基準だと、資産を隣接ディレクトリへ移すだけで測定からは消えて U=1.0 になり、消滅と隠蔽が区別できなかった。listing 基準なら、隠したときはロードもされていないので分母から外れるのが正しい
- 鮮度係数（90日 / 90日超）を削除した。保持期間14日の環境では原理的に判定できず、常に1.0にしかならない
- skillUsage（実測77件）は補助照合にのみ使う。プロジェクト横断のグローバル値であり、かつローカルの平文 JSON なので書き換えが容易

### 採点方法
0-100。Tier: 85以上 Lean / 70-85 Healthy / 55-70 Heavy / 40-55 Bloated / 40未満 Critical。

skill_listing の content が 20,001字ちょうどで切れている場合（実測でこの値に張り付いた）は截断と判定し、「肥大の上限側は測定不能・上限扱い」と明示する。

資産を1つも持たない環境は U を欠測にして台形スコアのみで採点する。

### 初回計測時の扱い
初回から算出できる。2回目以降は FC と U、および軸6の副作用（指摘のたびに指示書が伸びていないか）を追う。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| 指示書を短くしてフック注入や別ファイルの Read に逃がす | FC を実効入力トークンで測るので、経路を問わず乗る |
| 無害な hook を全イベントに刺して U を1にする | 本数に一切加点していない。注入した文字数は入力トークンに乗って台形の右側を落とす |
| 資産を別ディレクトリへ移して分母から消す | 分母を skill_listing に変更済み。隠した資産はロードもされないので、隠蔽と棚卸しが同値になり攻撃の旨味が消える |
| skillUsage を手で書き換える | 主源を attributionSkill に置き、skillUsage は補助照合のみ |
| 使わない資産を削除して U を上げる | 製品が意図する正しい行動なので許容する。ただし U と絶対資産数の推移を必ず並記し、削除は「棚卸しで改善」とラベルする。数を減らすこと自体には加点しない |

### 低スコア時のアドバイス（文面例）

例1
「1タスクあたりの実効入力が中央値 168k トークン（目安 40k）です。内訳を見ると、常時ロードの静的文字数は43,625字で、そのうち rules/capabilities.md の 8,900字は直近窓の依頼の12%でしか実際には参照されていません。@import を外してオンデマンド参照に降格させてください。」

例2
「定義81スキルのうち、窓内に一度も発火していないものが10本あります（daily-review, email-autoreply, lecture-minutes ほか）。共通点は description に起動条件が書かれていないことです。3本を archive/ へ移すと、毎セッション先頭に載るスキル一覧が約1,800字減ります。あわせて UserPromptSubmit フックが毎プロンプト平均1,058字を注入しています。起動時1回で足りる内容なら SessionStart へ移してください。」

## 9. 軸6 再発防止率（Recurrence Prevention）／ 両方 / 重み13

統合案の「学習定着率」を組み替えたもの。実装レンズが致命的な実測を出した。統合案どおりに実装すると、否定的リダイレクト142件のうち同一セッション内で永続層への書き込みが続いたのは1件（0.7%）だった。式は 0.45 を基準に置いており、60倍のスケール違いになる。全ユーザーがこの項でゼロになる。加えて Phase 1 が根拠にした16%は「永続層に限らないあらゆる Edit/Write」を数えた別の量だった。

そこで、分子を「書いたか（極端に稀）」から「同じものがまた出たか（十分な件数がある）」に入れ替えた。これは製品が売りたい物語（同じ失敗がもう起きない）そのものでもある。

### 問い
先月と同じ失敗、同じ指摘が、まだ出ているか。

### データ源
- 軸2で作ったエラー署名（実測491エラー）
- 軸1で判定した誘発型再編集の file_path
- P1 を通した人間発話のクラスタ
- 前窓スナップショットの署名集合

### 算出式

```
# 3系統の署名。窓ごとに「2回以上出たもの」を集合 S_t とする
E: エラー署名        (tool_name, error_class, target_kind)
P: 誘発再編集の対象パス（ソルト付きハッシュ）
H: 人間指摘クラスタ
   文字3-gram の MinHash（類似度0.75）と、
   固有名詞・パス・コマンド名の共起集合の Jaccard（0.6）を並行で取り、
   帰属の max を採用する
   ※「そのファイル」「例のやつ」と代名詞化しても、対象語が同じなら共起側で捕捉する
   ※ 計算は LSH バケット内でのみ比較し、全対比較はしない

r_cross = |S_t ∩ S_(t-1)| / |S_t|        # 窓を跨いで持ち越した割合

# 説明反復（人間側の内訳）
L3 = (2セッション以上に跨るクラスタに属する発話数 - そのクラスタ数)
     / 30字以上の人間発話数
     ※ 分母を「30字以上の実質発話」にする（相槌で分母を膨らませる水増しを無効化）
     ※ スキル起動 / attributionSkill が付いた定型トリガー（「朝ブリよろしく」型）は
       クラスタから除外する。これは契約をスキルに移しきった成熟した使い方であって、
       説明の反復ではない

score = 100 * ( 0.70 * (1 - r_cross) + 0.30 * (1 - min(1, L3 / 0.25)) )

# 初回窓（r_cross が存在しない）
score = 100 * ( 0.70 * (1 - r_in) + 0.30 * (1 - min(1, L3 / 0.25)) )
        ※ r_in は軸2の窓内再発率。「基準値を登録しました。次回は、
          これらが消えているかで採点します」と明示する
```

### 閉鎖の証拠は採点しない（診断注記に降格）

否定的リダイレクトの後に永続層（CLAUDE.md / .claude 配下 / AGENTS.md / メモリ系）へ書き込んだかは、実測で件数が足りず採点に使えない。診断としては価値があるので、次の形で注記だけ出す。

```
閉鎖と認める条件（厳格）:
  否定的リダイレクトの後に永続層へ write があり、
  かつ その write 先が以後のセッションで実際にロードされている
      （常時ロード層に含まれる / 発火したスキル・フックの本体である）
  かつ 同じ指摘クラスタへの追記が初回である
      （2回目以降の追記は「何度も書き足している」＝定着していない）
```

読まれない場所への追記は閉鎖と認めない。ここを緩めると、否定語を検知して .claude 配下のメモに1行 append するフックを5行書くだけで最重の軸が満点になる。

### 採点方法
0-100。Tier: 80以上 Systematized / 60-80 Closing / 40-60 Reactive / 40未満 Repeating。

署名が窓内10未満の環境は「再発の材料が少ない」として上位側（A相当）で扱い、分母不足の注記を付ける。欠測にして0点にはしない。上達しきったユーザーほど値が消える設計にはしない。

必ず「持ち越した署名」を件数順に上位3件、実名で出す。

### 初回計測時の扱い
初回は r_in ベースの暫定スコアと、〈未閉鎖の指摘クラスタ上位3件の実発話引用〉〈定着候補5件〉をローカル表示する。初回レポートは「今の写真＋次回の答え合わせ予約リスト」になる。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| 指摘のたびに指示書へ1行 append する | 閉鎖の証拠を採点に使わない設計に変えたので、書いても点にならない。書いた分は軸5の実効入力トークンに乗る |
| 否定語を使わない話し方に切り替えて分母を消す | 署名の主系統がエラー署名と誘発再編集パス（言い方に依存しない行動側）なので、人間の言い回しを変えても r_cross は動かない |
| 言い回しを毎回変えて人間指摘クラスタを逃れる | 文字 n-gram と、固有名詞・パス・コマンド名の共起集合の並行クラスタリングで max を採る |
| 相槌を大量に打って L3 の分母を膨らませる | 分母を30字以上の実質発話に限定 |
| スナップショットの署名集合を空にして r_cross を 0 にする | 軸0の hash chain。chain が壊れると percentile 参加資格を失う |

### 低スコア時のアドバイス（文面例）

例1
「前の窓で2回以上出た失敗のうち、64%が今の窓でも出ています。最多は Edit の『String to replace not found』を .md ファイルに対して出しているもので、前窓23件・今窓19件。これは文章で書いても止まりません。PreToolUse の Edit フックで直前 Read を検査してください。」

例2
「『議事録に transcript を並置していない』という同じ指摘が、3セッションにまたがって出ています。指示書には反映されていません。これは散文でなく、PostToolUse フックで『minutes を書いたら同名 transcript の存在を検査する』に変えると機械で止まります。あわせて、あなたが手打ちしている定型の前置き3文が11セッションで反復しています。これを CLAUDE.md に移せば毎回の手打ちが消えます。」

いずれも主語はエージェント側に置く。「あなたが学習していない」ではなく「これを入れればエージェントが繰り返さなくなる」と書く。

## 10. 軸7 依頼の設計度（Request Design）／ 人間側 / 重み12

### 問い
依頼の起点に、対象・制約・完成条件が入っているか。

### データ源
P1・P2 を通した人間発話のうち、「新しい依頼の起点」になったもの（直前が自分の発話でないもの）。実測で人間発話は2,848件あり、初回発話だけに限定した場合の分母不足を回避できる。

ローカル解析のみ。外部に送るのは 0-2 の整数スコアと集計値だけで、本文もそのハッシュも送らない。

### 算出式

決定論的な採点を主にする。ローカル LLM が使える環境ではルーブリック再採点し、決定論版との差はキャリブレーションにのみ使う。外部 LLM は使わない。

```
Context (0-2)
  0 = 対象の特定なし
  1 = 実在するファイルパス / URL / 固有名詞のいずれかが1つ以上
  2 = 対象の特定 + 根拠の提示（コードフェンスの同時出現）
      ※ attachment との紐づけは諦める。attachment レコードは人間発話と別レコードで
        流れ、外部キーが無い（parentUuid が付かないものがある）

Specificity (0-2)
  制約表現の出現数 m
  （出力形式 / 件数・数量 / 期限 / 除外表現「〜は触らない」「〜だけ」/ 使用ツール指定）
  m = 0 → 0 / m = 1-2 → 1 / m >= 3 → 2
  ※ 20字未満で自動0にする規則は撤廃した。日本語は同じ情報量を英語の1/3〜1/4の
    文字数で書けるため、文字数の足切りは日中韓のユーザーを構造的に低く出す

Verification (0-2)
  合否条件の明示（「〜になればOK」「テストが通ること」「期待する出力は」「〜と一致」
  「例:」「should」「expected」または期待値のコードブロック）
  0件 → 0 / 1件 → 1 / 2件以上または期待出力の具体例あり → 2

# 制約の遵守で掛ける（書いただけの空文句を無効化する）
C_obey = 制約表現を含む依頼のうち、その制約が実際に守られた割合
         「tests/ は触らない」と書いた回に tests/ への編集が無かったか
         「3件まで」と書いた回の出力が3件以内だったか

score = 100 * (1.0*C̄ + 1.0*S̄ + 0.6*V̄) / 2.6 * (0.8 + 0.2 * C_obey)
```

Verification の重みを 0.6 に落とすのは、最も効果量が大きい軸でありながら自動判定の人間一致が最低（重み付きκ=0.316）で、素朴に採点するとノイズ最大の軸が看板になるため。

### 採点対象から外すもの

- スキル起動 / attributionSkill が付いた依頼。契約はスキル側にあるため、これを採点対象にすると、出力契約をすべてスキルに移しきった最も成熟した使い方が0点になる。実測でこの環境の反復初回プロンプトの実質唯一の人間由来例が「朝ブリよろしく」（7文字）だった
- 定型前置き。文字列類似度ではなく構造の同型性（制約語のスロット位置・順序・個数のパターン一致）で検出する。同義語をローテしても逃げられない
- 手戻りが起きていない低スコア発話。短くて済んでいるのは良いことなので、指摘しない

### 環境側への付け替え

UserPromptSubmit フックや CLAUDE.md にプロンプト自動整形の指示が存在する環境は、本軸を人間側から環境側へ付け替え、「この環境ではプロンプト整形が自動化されているため人間側スコアとして扱わない」と明示する。人間側スコアが環境の1行設定で最大化できる状態を放置しない。

### 採点方法
0-100 と C/S/V の3軸内訳を必ず併記する。合計だけ出すと何を直せばよいか分からなくなる。

Tier: 85以上 Specified / 65-85 Scoped / 45-65 Directive / 45未満 Vibing。

加えて「起点の平均」と「2発話目以降の平均」を並記し、その低下幅を出す。初回だけ整えて雑な依頼を2発話目以降に投げる逃げ道を可視化するため。

フィルタ後の起点発話が30件未満、または日本語・英語いずれの辞書にも該当しない言語の環境は欠測。日英以外は欠測になることを仕様として明記する。

母集団平均（外部研究の C=1.48 / S=1.08 / V=0.58）は、コード用途と判定された環境にのみ表示する。この効果量はコード文脈での実証であり、非コード用途への外挿は未検証であることを画面に明示する。

### 初回計測時の扱い
初回計測の主役。初回から出る。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| 5行の定型ヘッダを毎回貼る | 良性のゲーム化として許容する（貼るのは正しい行動）。ただし構造同型性で検出して採点対象から外し、「そのテンプレは CLAUDE.md に移せば毎回貼らなくて済む」と誘導する。ハックの先に次の改善提案が待つ構造にする |
| CLAUDE.md やフックでプロンプトを自動整形させ、人間側スコアを機械に作らせる | 検出したら人間側から環境側へ付け替える |
| 初回だけ整えて2発話目以降で崩す | 観測窓を全ての起点発話に広げ、低下幅を主表示にする |
| 制約表現を書くだけ書いて守らせない | C_obey を掛ける |
| 文字数を水増しする | 3軸とも出現数カウントで、長さは加点しない |

C/S/V が高いのに軸1の誘発型手戻りも高い環境は「形式は整っているが意図が伝わっていない」として別分岐にし、褒めない。

### 低スコア時のアドバイス（文面例）

例1
「Verification が 0.3/2 です。完了条件が書かれていません。前回の『議事録作って』を、こう書き換えてください。『議事録作って。完了条件: 参加者全員が発言者として登場、決定事項は3件以内、transcript を同フォルダに並置』。この1行の有無で、書き直し回数が変わります。」

例2
「Context 0点の依頼が41%あります。『あのファイル』『さっきの件』で始めた回の書き直し回数は、パスを書いた回の2.4倍でした（あなた自身のログでの実測です）。もう一つ、Specificity は『触らないもの』を1つ書くのが最も効きます。『tests/ は変更しない』の一言で足ります。」

必ず本人の低スコア発話1件を引用し、書き換え例を並べる。自己評価と実力はほぼ無相関（相関 0.07〜0.24）で、低スコア者ほど自分を過大評価する。証拠なしの数字は拒絶される。

## 11. 軸8 手離れ度（Hand-off）／ 人間側 / 重み8

統合案の「監督バランス」を解体して作り直した。旧軸は3レンズすべてから同じ点を突かれた。

- 無検討承認の判定は、返事を31字にするだけで減点30が丸ごと消え、しかも読んでいるかとは無関係だった
- 制止介入率は、実測で分子が31件/14日しかなく加点が常時0で、しかも処方が「摩擦を増やせ」になっていた
- 加えて、人の注意力を採点していること自体が製品の倫理条件と衝突していた

そこで、人を採点する要素（読んだか / 止めたか）を全部落とし、「1つの成果物にどれだけ張り付いたか」だけを残した。母集団順位は付けず、自分の窓間比較を主表示にする。

### 問い
成果1件を出すのに、どれだけ発話し、どれだけ画面の前にいたか。それは前回より減っているか。

### データ源
- P1 を通した人間発話数
- 軸1で判定した誘発型のやり直し（否定語辞書に依存しない）
- 生成中断 [Request interrupted by user]（実測20件）
- assistant 最終 timestamp から次の人間発話 timestamp までの差
  （実測 p25 51.7秒 / p50 152.1秒 / p90 1,019.8秒）
- SA（P6）

### 算出式

```
# 人手コスト
HTC = (人間発話数 + 2 * 誘発型やり直し数 + 3 * 生成中断数) / Σ w(SA)

# 拘束時間
WT = Σ think-time / Σ w(SA)
     think-time は 15秒以上 60分以下のものだけを合算する
       15秒未満: 読んでいない可能性と読み終えている可能性を区別できないので使わない
       60分超  : 離席として全計算から除外する

# 初回
score = 50 固定（基準値の登録のみ。総合点の分母から外す）

# 2回目以降（自己相対）
score = 50 + 50 * clip( 0.65 * (前窓HTC - 今窓HTC)/前窓HTC
                      + 0.35 * (前窓WT  - 今窓WT )/前窓WT , -1, 1 )
```

母集団の絶対値比較は、同一言語コホートで基準値が貯まるまで行わない。

### 採点しないが必ず出す内訳

- 前進発話 / やり直し発話 / 生成中断 の3分割
- 危険操作を止めた回数（ツール中断 + user-rejected）。加点も減点もしない事実表示にする。旧設計では「止められた回数」を美徳として加点しており、それは「摩擦を増やせ」というアドバイスに直結して、permissions を実運用に磨いた人ほど無監督扱いになっていた
- 相対否定比（否定数 / (否定数 + 肯定ack数)）。文体差の系統誤差をならすための参考値で、Tier を動かす後処理はしない。後処理で Tier を上下させると、スコアの意味が不定になる

### 採点方法
0-100。Tier: 80以上 Hands-off / 60-80 Watching / 40-60 Hands-on / 40未満 Attached。

SA が0件、または人間ターンが窓内5未満の環境は欠測。

### 初回計測時の扱い
初回は絶対値の採点をせず、内訳表示と基準値の登録に留める。総合点の分母からも外し、2回目から参加させる。

### ゲーム化耐性と硬化策

| 攻撃 | 硬化策 |
|---|---|
| 何も言わずに放置して自動で回す | 発話は減るが SA も減るか、軸1の書き直しが増えて相殺される |
| 介入せず黙って自分で書き直す | edited_text_file の出現を軸4で拾っており、「介入が少ない × 人手編集の痕跡あり」を別表示にする |
| SA を水増しして分母を膨らませる | P6 の受領シグナルで 0.4 に減衰。軸1・軸4と共通の分母なので、1箇所の硬化で3軸に効く |
| think-time を稼ぐために放置する | think-time は 15秒〜60分にクリップし、長い側を加点しない |
| 返事を長くする / 短くする | 返事の長さを一切見ない（旧設計の30字条件は撤廃した） |

### 低スコア時のアドバイス（文面例）

例1
「成果1件あたり6.2発話、うち2.1回がやり直しでした。やり直しの発生位置は平均2手目で、方向のズレが早期に出ています。初回指示に『やらないこと』を1行入れるだけで消える型です。」

例2
「1成果物あたりの拘束時間が前回の38分から52分に伸びました。伸びた分の大半は、差分が100行を超える出力の直後にあります。『差分が100行を超えたら、変更点を3行で先に出す』を出力契約に入れると、確認の負荷が下がって拘束時間が短くなります。」

断定表現（「読んでいませんね」）は製品側で禁止する。チーム内での人間スコア順位表示機能と、雇用主が個人スコアを閲覧する機能は実装しない。

## 12. 安全チェック（非採点）

旧「ガードレール実効度」軸。採点軸から外した理由は第15節に書く。ここでは「設定しているつもりで壊れている」という嘘の解消だけを、順位を付けずに実名で警告する。

出すのは3つだけ。いずれも存在チェックで水増しできず、直す行動が実際の改善になる。

### (a) bare allow による scoped 設定の無効化
4スコープ（enterprise managed / ユーザー設定 / プロジェクト設定 / ローカル設定）をマージした permissions.allow に、括弧なしのツール名（Bash / Read / Write 等）が1つでもあれば、その配下の細粒度エントリは全部効いていない。実測でこの環境は allow 263件のうち scoped 204件がこれで死んでいた。

文面例:「permissions.allow の Bash という1行が、その下の scoped 204件を全部無効にしています。この1行を消してください。消しても許可が減るだけで、何も壊れません。」

### (b) 参照先が存在しない hook 登録
hook の command からスクリプトパスを解決（環境変数を展開）して存在確認する。不在なら、そのガードレールは登録されているだけで動いていない。

### (c) hook_cancelled によるサイレント無効化
hook_cancelled を hookName 単位で集計し、cancelled/(success+cancelled) が 0.3 を超えるフックを実名で列挙する。実測で PreToolUse:Edit は cancelled 108件に対し success 27件で、8割の確率で無効化されていた。

文面例:「check_layer_b_access は timeoutMs 5,000 に対して実測6,167ms かかり、窓内59回サイレントに無効化されています。設定上は守られているが、実際には守られていません。起動時1回のキャッシュ方式に変えるか、PostToolUse へ移してください。」

環境全体の比率で採点はしない。閾値5%のような全体比率で採点すると、フックを1本でも重く書いた環境が全部床に張り付いて識別力が消える。

### 併記するもの
設定ファイルの mtime と各セッションの timestamp を突き合わせ、「その設定が実際に有効だったセッションの割合」を併記する。窓の最後の1日に置かれた設定は、当該窓ではほとんど効いていない。

### hook のレイテンシについて
データ源が2つあり、実測で21倍食い違った（lastSessionMetrics の p95 = 776ms に対し、hook_success の durationMs 全件集計は n=4,149 で p95=16,127ms）。どちらが実時間かを確定するまで、レイテンシは警告に使わない（未解決リスク #4）。使うと決めたら hook_success の durationMs に一本化し、必ず float キャストして失敗は欠測にする（hook_success では文字列、hook_cancelled では数値で型が揃っていない）。

### 欠測処理
どの軸も「持っていない」と「持っているが低質」を厳密に分ける。欠測軸は分母から外し、残りの重みを再正規化する。0点にはしない。分母を固定すると、CLAUDE.md 1枚だけの健全なユーザーが測定不能か0点になり、製品が成立しない。

欠測が3軸を超えた環境は、総合点を出さずに軸別の内訳だけ返す。欠測が増えるほど残り軸の重みが跳ね上がってノイズが増幅するため。

### 表示
- 総合 0-100 と S/A/B/C/D の5段 Tier
- 〈帰結スコア（軸1・2・3・4の加重平均）〉×〈設計スコア（軸5・6・7・8の加重平均）〉の2次元散布を必ず併示する。「同じ帰結を、もっと軽い環境で出している人がいる」という見せ方は順位より刺さる
- 2回目以降は各軸の前窓比Δを主表示にする。ただし各軸の分母からブートストラップ信頼区間を出し、区間が重なるΔは「変化なし」と表示する。実測で否定的リダイレクトは85.7%のセッションでゼロという極端に薄い分布であり、小分母のΔは大半が測定ノイズである
- 対照基準を必ず併記する。設定ゼロの素の環境を同じ式に通したときの各軸スコアを製品側で固定値として算出し、「あなたは基準の +18点、うち14点は設定ではなく運用で稼いでいる」と言える形にする。これがないと「設定を凝っている人が高得点になる装置」という批判に答えられない

## 14. 相対評価の段階設計

分母がゼロの初日から偏差値の公表までを3段階に分ける。段階を飛ばさない。

### 段階1: Tier制（母集団 0件から）

- 各軸を S/A/B/C/D の5段で返す。閾値は本設計書に書いた絶対値
- 総合も5段 Tier
- 母集団への言及は一切しない。「あなたは上位◯%」と書かない
- 主表示は「実名で挙がった直すべき箇所」と「前窓比Δ」
- 外部研究の分布（AI習熟度1,800件で平均48・中央値48・最上位1.3%）は Tier の形状を決める参考にはするが、数値そのものは借りない。測っているものが違う

段階1で製品として成立させる。母集団比較がなくても、実名の指摘とΔだけで価値が出る形にしておく。

### 段階2: 到達率（同一言語コホート・同一用途プロファイルで n≧50）

- 順位ではなく二値の到達率で出す。「この軸で B ランク以上に到達している人は全体の34%です」
- 到達率なら小標本でも壊れにくい。percentile は分布の裾で暴れる
- コホートは〈言語 × 用途プロファイル（コード / 文書 / 調査 / 混在）〉で切る。切らないと、非コード用途のユーザーが構造的に低く出続ける
- 参加条件: 軸0のゲート通過（整合性85以上）

### 段階3: percentile（同一コホートで n≧300）

- ここで初めて偏差値・percentile を名乗る
- 参加条件: 軸0のゲート通過に加えて、連続2窓以上の hash chain 保持
- 軸ごとに n≧300 を満たしたコホートだけが percentile 表示になる。満たしていない軸は段階2のまま混在表示する
- percentile を出しても、2次元散布（帰結×設計）の併示はやめない

### 全段階で守ること
- 人間側2軸（軸7・軸8）のチーム内順位表示は、どの段階でも実装しない
- 雇用主が個人スコアを閲覧する機能は実装しない
- 「生産性が何%上がった」は名乗らない。反事実が原理的に取れず、外部の RCT では実測19%減速に対して体感20%高速化という約39ポイントの乖離が観測されている。本製品は相対位置と自己時系列比較に徹する

## 15. 落とした軸と理由（rejected）

復活の判断材料として残す。

### ガードレール実効度（統合案の軸5・重み10）
判定: 採点軸から外し、非採点の安全チェックに降格。

理由。3レンズのうち懐疑的ユーザーが kill、他2つも revise だが指摘の中身は同質だった。
- 減点8項のうち5項（合計マイナス95点相当）が静的ファイルの中身を見ているだけで、測定の直前に設定ファイルを差し替えれば満点になる。「実効度」という名前を付けているぶん質が悪い
- 素の Claude Code をインストールしたまま使うと、deny/ask のカテゴリ未被覆でマイナス60、結果40点の最低 Tier になる。箱から出したままの正しい状態が最低評価になる
- 点が上がる唯一の行動が「設定に deny 行を書く」「hook を置く」であり、それをやっても成果物の質は変わらない。製品が最初に否定した既存スコアカード（50点中46点がファイル存在チェック）と同じ場所に着地していた
- 何もしない空フックを3イベントに置くと、停止位置・タイムアウト率・レイテンシの3項が同時に満点になる
- レイテンシのデータ源が2つあり実測で21倍食い違う

復活の条件: hook がブロックした実績（exit 2 相当）の記録形式が実データで確定し、「止めるべきものを実際に止めた回数」が作動証拠として取れるようになったら、静的減点をやめて作動証拠だけの加点軸として復活させる余地がある。

### 監督バランス（統合案の軸8・重み8）
判定: 解体して「手離れ度」に作り直した。

理由。
- 無検討承認の判定（大出力 × think-time 15秒未満 × 30字未満の ack）は、返事を31字にするだけで減点30が消える。しかも実測で think-time の p25 が51.7秒であり、15秒未満はほとんど発生せず、減点30点分が死に項だった
- 制止介入率は実測で分子が31件/14日、加点は常時0付近。しかも処方が「permissions.ask に入れて摩擦を増やせ」になっており、permissions を実運用に磨いた人ほど無監督扱いになる符号の反転があった
- think-time による「読まずに承認」判定は離席と原理的に区別できない。人の注意力を採点すること自体が製品の倫理条件と衝突する

残したもの: 1成果あたりの人間発話数と拘束時間（自己時系列のみ）。落としたもの: 制止介入率の加点、無検討承認の減点。

### 学習定着率の閉鎖率ベース定義（統合案の軸7の中核・重み18）
判定: 定義を再発ベースに組み替え、閉鎖率は診断注記に降格。重みも18から13へ。

理由。実装レンズの実測が決定的だった。
- 統合案どおりに実装すると、否定的リダイレクト142件に対し永続層への書き込みが続いたのは1件（0.7%）。式は 0.45 を基準に置いており60倍のスケール違い
- Phase 1 が根拠にした16%は「永続層に限らないあらゆる Edit/Write」を数えた別の量で、学習とは無関係だった
- 否定的リダイレクトの検出範囲を仕様に書いていないだけで値が3倍動いた（先頭400字で90件 / 全文で142件 / Phase 1 は288件）
- .claude 配下のメモに1行 append するフックを5行書けば最重の軸が満点になり、しかも追記文字数は静的な文脈税の計算対象外だったので相殺が成立していなかった

軸の名前と物語（同じ失敗がもう起きないか）は残す価値があるので、分子を「書いたか」から「また出たか」に入れ替えた。

### 成果レバレッジ（トークン / SA の独立軸化）
理由: 作業の難易度で正規化できないという母集団比較の構造的な急所を最も強く受ける。軽い仕事しかしていない人が高スコアになる。加えて「トークンを減らせ」は行動に落ちない。軸1の補助表示としてのみ残した。難易度の代理変数が確立できたら復活の価値がある。

### 指示書の行動可能性（具体性密度 / 抽象語密度 / 内部重複 / 数値ドリフト）
理由: 辞書が言語依存で非英語ユーザーに系統的バイアスが出る。抽象語密度は書き手の文体を測ってしまう。最も価値のある部分（壊れた参照・公式基準違反）は軸5の静的欠陥項に、数値ドリフトは軸6に吸収できる。多言語辞書が整備できたら独立軸に戻す候補の筆頭。

### 量への加点全般（トークン総量・支出額・セッション数・スキル本数・hook 本数・permissions 件数・CLAUDE.md 行数）
理由: すべて「量」で、水増しツールが数時間で作れる。実測でも保有量と実効性は完全に乖離していた（スキル81本中10本が未起動、hook が59回タイムアウトで無効化、scoped 204件が bare 1行で全滅）。8軸の算出式のどこにも「増やすと得をする項」が存在しないことを設計の不変条件として固定する。

### TodoWrite の完了率を主軸に置く案
理由: status を completed に書き換えるだけで満点。ゲーム化耐性が全指標中で最低。軸3の固定小減点として残すのみ。

### permissionMode の bypassPermissions 比率を独立の安全性軸にする案
理由: 隔離環境やコンテナなら合理的な選択で、文脈なしには善悪が判定できない。分布も二極化して識別力がない。安全は順位を競うものではない。

### キャッシュ効率（cache_read の比率）
理由: 新規セッションを立てる頻度という作業パターンに強く依存し、指示書の質より働き方の癖を測る。軸5の内訳表示のみ。

### モデル使い分けの適切さ
理由: タスクの重さをログから推定する手段が無く、正解が定義できない。定額プランか API 従量かでも最適解が反転する。

### サブエージェント / Workflow の委譲効率
理由: 使っている環境が少数派で、必須軸にすると「使っていないだけ」を低評価する。加点のみ・減点なしの成熟度バッジとして別枠表示する。なお isSidechain は実測で全レコード false だったため、サブエージェント検出には使えない。

### Tool Correctness / trajectory match / pass^k / cost-of-pass
理由: いずれも参照解（expected_tools、reference trajectory、正答確率、同一タスクの反復実行）を要求する。個人環境に golden dataset も反復実行も存在しない。pass^k の思想（平均でなく毎回きちんとやる）は軸6の窓跨ぎ持越率が最も近い役割を担う。

### git revert率 / code turnover / マージPR帰属 / suggestion accept rate
理由: 分母がコード成果物に固定されており、メール・議事録・記事・スライドが主用途のユーザーで分母が消滅する。公式の contribution metrics は Team/Enterprise + GitHub App + Owner 権限が必須で個人環境では取れない。SA 定義で置き換えた。

### OpenTelemetry 系メトリクス
理由: code_edit_tool.decision の accept/reject と source 内訳は、ガードレールが機能したかを直接測れる唯一の一次データだが、テレメトリの事前有効化が必須で遡及取得できない。初回診断が空になるため軸に置けない。「有効化すると次回からこれが測れます」という段階提示に回す。

### stats-cache.json / history.jsonl / projects[].history と last* 系
理由: 実測で4ヶ月以上更新が止まっており（totalSessions 21 / costUSD 0）、history は VS Code・SDK 経路で空、last* は直近1セッション分のみ。構造が整っていて誘惑が強いため、指標源から明示的に排除する。

### カスタムログを前提にした全指標
理由: 本環境には176,585件の hook イベントログがあるが、赤の他人の環境には存在せず汎用性要件に反する。同等情報は Claude Code 自身が書く attachment から取れる。

### CLAUDE.md の意味的矛盾検出
理由: LLM 判定でしか掴めず、本文を外に出さない方針と決定論的な再現性の2条件と衝突する。ローカル小型モデルは環境依存が大きすぎる。

### 人間の内面（出力評価力・限界認識・AI基礎知識・ツール理解）
理由: ログには「何をしたか」しか残らず「なぜそうしたか」は現れない。20〜40分の対話でしか判定できない。

### ピア調査（誰の使い方を真似たか）
理由: 個人向け製品には同僚がいない。チーム版が出るまで測定対象外と明示する。

### 生産性向上率・時間削減効果
理由: 反事実が原理的に取れない。自己申告での代替も不可（体感と実測の乖離が約39ポイント）。

### 静的スコアカード型の総合採点
理由: 50点中46点がファイル存在チェックで、質を測ると名乗る製品が踏んではいけない罠そのもの。ただしベンダー一次情報の数値基準（SKILL.md 500行以下 / description 1024字以内 / 参照は1階層 / 100行超の reference に目次）だけは軸5の静的欠陥項の閾値根拠に借用した。

### 偏差値・percentile の即時表示
理由: 分母がゼロから始まる。第14節の3段階で昇格させる。

### タスク難易度による正規化
理由: 落としたのではなく、実装できないことを製品仕様として明示する残課題。3レンズとも解を出せなかった。当面は Tier 制、軸1の内訳分解、2次元散布、用途プロファイル別コホートで緩和するに留める。

## 17. 実装の最小形（Phase 0）

需要検証に必要なのは全8軸ではない。「実名で指摘され、直したら次回下がる」が1周回ることを見せられればよい。

### Phase 0（この5つで需要検証する）

| 優先 | 何を作るか | 理由 |
|---|---|---|
| 1 | 軸0のゲートと共通土台（P1〜P8 + スナップショット） | これがないと「スコアが低い」のか「測れなかった」のかを誰も区別できない。SA 定義（P6）は軸1・4・8の共通分母なので、後から変えると全部作り直しになる |
| 2 | 軸2 空振り率 | 実測で分子分母とも件数が最も安定している（18,241呼び出し / 491エラー）。初回から出て、エラー分類の実名上位3件がそのまま行動になる。最初の刺さる画面を最も安く作れる |
| 3 | 軸1 一発着地率 | 深度の実名列挙（このファイルを14回書き直しています）が最も分かりやすい。SA 定義の妥当性をここで実地に検証できる |
| 4 | 軸7 依頼の設計度 | 人間側の主役。初回から出て、書き換え例の提示という具体的なアウトプットになる。製品の4つ目の売り（人間側アドバイス）をここだけで成立させられる |
| 5 | 安全チェック3項目 | 実装が最も軽く（設定ファイルのマージと存在確認だけ）、しかも「bare allow 1行で204件が死んでいる」型の発見はインパクトが大きい。採点しないので設計の議論を止めない |

Phase 0 の総合点は、軸1・軸2・軸7 の3軸を重み再正規化（15 / 14 / 12 → 37 / 34 / 29）して出す。ただしこの段階では総合点を前面に出さず、〈実名の指摘リスト〉と〈次回ここを見ます〉を主表示にする。

Phase 0 でも、8軸すべての分子分母のスナップショットは取る。後から遡れないため、記録だけは初回から全軸ぶん行う。
